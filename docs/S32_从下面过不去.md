# S32 —— 「从上面能过去，从下面就是一直卡在这里」

> 用户原话（2026-11-10 夜，附 RViz 截图）：
> 「从上面能过去，从下面就是一直卡在这里」

这句话是本项目到目前为止**最有价值的一句反馈**。
它把「导航失败」这个笼统的现象，瞬间收敛成了一个可计算的问题：
**同一条缝，为什么两个方向的可通行性不一样？**

答案不是调参，是**车体模型的错**。

---

## 一、先看证据：车到底停在哪、为什么停

截图里红色菱形（车）停在 `partition_short` 南端偏西，约 `(0.9, -1.6)`。
对应的 `live_nav.log` 显示：

```
[controller_server]: Failed to make progress          ← 第 5 次，连续 5 次
[controller_server]: [follow_path] Aborting handle.
[local_costmap]: Received request to clear entirely the local_costmap
[planner_server]: GridBased: failed to create plan with tolerance 0.50.
[planner_server]: Planning algorithm GridBased failed to generate a valid path to (2.20, -1.50)
   ↑ 连续 5 次，每次都清一遍全局代价图再试，仍然画不出来
[behavior_server]: Running spin
[behavior_server]: Collision Ahead - Exiting Spin     ← 想原地转，被判定前方有碰撞
[behavior_server]: spin failed
[behavior_server]: Running backup
[behavior_server]: Collision Ahead - Exiting DriveOnHeading   ← 想后退，同样被否
[behavior_server]: backup failed
[bt_navigator]: Goal failed
```

**三条恢复行为（spin / backup / wait）全部失败**，这本身就是信号：
不是「控制器选错了轨迹」，而是**车周围根本没有合法空间**。

### 关键一步：把车的实际坐标代进代价图

日志里车最终停在 `(0.97, -1.81)`。用 `room_geom.inflate_cost` 算这一带：

| 位置 | 车心净空 | 代价 | 判定 |
|------|---------|------|------|
| (0.92, -1.81) | 0.198 | **253** | 致命 |
| (0.97, -1.81) | 0.148 | **253** | 致命 |
| (1.00, -1.81) | 0.118 | **253** | 致命 |
| (1.05, -1.81) | 0.069 | **253** | 致命 |

再沿 y = −1.81 这一行横向扫一遍，看非致命段在哪：

```
y=-1.81  非致命段: [0.60, 0.91], [1.52, 2.75]
```

车在 **0.97 —— 两段之间的死亡地带里**。
左边是墙那边的通路（但西侧到不了板东），右边才是它想去的地方。

> **车不是「慢慢地过不去」，是「站在一个代价 253 的格子上」。**
> 任何一条候选轨迹的末端点只要落在车心附近，`BaseObstacleCritic::scorePose()`
> 就会 `throw IllegalTrajectoryException` —— 全车淘汰。
> 于是 DWB 输出 v=0、w=0；`progress_checker` 判卡住；
> 恢复行为也因为「前后左右都是 253」而全部 `Collision Ahead`。
>
> **这就是为什么三种恢复全失败**：它们不是不走，是真的没地方走。

## 二、根因：车被当成一个 0.20 m 的圆

之前所有代价地图配置都是：

```yaml
robot_radius: 0.20     # 0.30 × 0.24 车体的外接圆半径 0.192，取 0.20 留余量
inflation_radius: 0.22
```

这套写法在**开阔区域**完全没问题，但在这个房间里塌了。

### 2.1 圆模型对「贴边」是灾难性高估

车体 0.30 × 0.24（`urdf/navbot.xacro` 的 `box size="0.30 0.24 0.06"`）：

```
外接圆半径       = sqrt(0.15² + 0.12²) = 0.192
车宽一半（贴边） = 0.12
         差距   = 0.072 m   ← 圆模型凭空多算了 7.2 cm
```

在一条 0.655 m 的缝里，多算 7.2 cm × 2 侧 = **14.4 cm 的假障碍**。

### 2.2 缝 S 的实际账

| 模型 | 车心合法带（宽 0.655 的缝） | 结论 |
|------|--------------------------|------|
| 圆 0.20 | 0.655 − 2×0.20 = **0.255 m** | 勉强，还要扣掉膨胀惩罚 |
| 矩形 0.30×0.24 | 0.655 − 2×0.12 = **0.415 m** | 宽裕 |

再叠加 `inflation_radius 0.22`（> 车半径，钱都花在「虚胖」上），
零代价带只剩 0.215 m，而**实际车身只需要 0.24 m 的总宽**——

> 也就是说：**车能过（0.24 < 0.655），但代价图认为它过不去（0.255 太窄且处处有代价）。**

### 2.3 为什么「从上面能过去」

板东侧通道 1.63 m 宽，扣掉膨胀还有 **1.19 m** 零代价带 —— 随便过。
所以从北往南（沿着板东侧直下）一路零代价，一路顺。

从南往西穿，要挤进那道**只剩 0.215 m 零代价带**的缝，
而且车头要从「朝西」掰到「朝北」（转 90°），
每一步都要在窄带里同时满足：位置在带内 + 朝向对 + 轨迹末端不落 253。

**两个方向的可通行性差了 5 倍**，这就是用户看到的「上面能过、下面卡住」。

```
                    北区（开阔）
    ─────────────────────────────────────
         partition_mid  y∈[0.455, 0.555]
    ─────────────────────────────────────
                          ┌──┐
                          │  │ partition_short
                          │  │ x∈[1.117, 1.317]
                          │  │ y∈[-1.795, 0.005]
                          └──┘
              车心合法区 y∈[-2.25, -2.00]    ← 只有 0.255 m 高
    ═══════════════════════════════════════
              wall_south  y = -2.45
```

车心要在这 0.255 m 高的夹层里完成「横穿 + 转身」，
而车身转 90° 时扫过的圆半径是 0.192 —— **余量只有 0.06 m**。

## 三、修法：把车体模型换对

### 3.1 两处代价地图都改

```yaml
# local_costmap 与 global_costmap 同步，必须一致
footprint: "[[0.15, 0.12], [0.15, -0.12], [-0.15, -0.12], [-0.15, 0.12]]"
#           ↑ 车头方向 ±0.15，车宽方向 ±0.12 —— 与 urdf box size 严格一致
```

**`footprint` 与 `robot_radius` 在 Nav2 里是互斥的**：
只要写了 `footprint`，`robot_radius` 就被静默忽略。
留着 `robot_radius: 0.20` 不会报错，只会让后来看配置的人以为它生效了。
所以这次**把 `robot_radius` 整行删掉**，而不是注释掉。

### 3.2 膨胀半径必须跟着降

这是最容易漏的一步。换了矩形足迹但保留 0.22，
膨胀层仍然按 0.22 往外推，缝 S 的账一点没变好。

```yaml
inflation_radius: 0.22  →  0.16
```

依据：矩形足迹的 `inscribed_radius = min(0.30, 0.24)/2 = 0.12`。
膨胀半径只要覆盖 `0.12` 加一点缓冲即可，取 `0.12 + 0.04 = 0.16`。

### 3.3 一个必须承认的副作用

`inflation_radius 0.16 < 圆半径 0.20`，意味着膨胀层的**衰减区被吃掉了**：

```
d < 0.20            → 253（致命）
0.20 ≤ d < 0.22     → 253·exp(-5(d-0.2))  ← 0.22 时这 2 cm 是软代价
d ≥ 0.22            → 0
```

改成 0.16 后并没有「0.20~0.16 的更软的一段」——
因为 `d < radius` 就是 253，`d ≥ inflation` 就是 0，中间没有区间。

**代价图从「253 → 缓坡 → 0」变成「253 → 0」的硬台阶。**

这不是 bug，是换取「缝能过」必须付的代价。缓解措施：

- `BaseObstacle.scale: 0.5`（S31 已设）让 DWB 主动远离 253 边界，
  硬台阶不会导致「贴着 253 走」
- 真机部署时，如果发现车角蹭墙，第一件事是把 `footprint`
  从 4 顶点改成 8 顶点（边中点也加上），让碰撞检测更密

## 四、判据：我之前的检查为什么全绿

这是这次最该记住的部分。

`room_geom.py` 里所有判据 —— `passable()`、`narrow_band()`、`inflate_cost()` ——
**算的都是「车心」这一个点**。

```python
free_cost = gap - 2 * inflation     # 0.655 - 0.44 = 0.215  ✓ PASS
```

判据说「0.215 > 0.1，缝 S 很宽裕」。
但车不是点。车横穿一道缝时，**车头进去、车尾还在外面**，
中间那一段必须让整个车身都落在非致命格里。

**判据算的是它想算的东西，算错了对象。**

### 4.1 新增的判据（room_geom.py 第 [5] 节）

```python
def body_min_clear(x, y, yaw):
    """车体矩形贴地面那段（8 个采样点）的最小净空。"""
    w, h = 0.30, 0.24
    pts = [(w/2, h/2), (w/2, -h/2), (-w/2, h/2), (-w/2, -h/2),
           (w/2, 0.0), (-w/2, 0.0), (0.0, h/2), (0.0, -h/2)]
    return min(clearance(x + dx*cos(yaw) - dy*sin(yaw),
                         y + dx*sin(yaw) + dy*cos(yaw))
               for dx, dy in pts)
```

断言三条：

1. 车心最高只能到 `y = -1.795`，再往上车体（沿 y ±0.12）压进板里
2. **缝 S 给车心的纵向空间只有 0.455 m**（y 从 −2.250 到 −1.795）
3. 板东通道 1.63 m，车心净空 0.233 > 车半径 → 宽敞，是主通路

第 2 条才是核心：**0.455 m 的纵向空间里要把车头从朝南掰到朝北**，
车身扫过半径 0.192 的圆 → 只有 `y ≤ -2.00` 时才能安全转身。
这比缝 S 的中线还低 0.20 m。

### 4.2 新增的判据（check_limits.py 第 ②b 节）

```python
# footprint 与 robot_radius 只能二选一
if fp_global and fp_local:
    ok('两处都用 footprint（矩形足迹），模型一致')
    ...
    if g_rr or l_rr:
        ng('同时存在 robot_radius —— Nav2 里两者互斥，'
           'footprint 存在时 robot_radius 被忽略，留着只会误导人')
```

外加一条**硬失败**：`inflation` 比车宽一半多出 > 0.10 m 就 FAIL，
理由直接写进报错信息里（「正是 S32 从下面过不去的成因」）。

### 4.3 故障注入扩到 9 种

```
[抓到] primary_controller 写成参数块名（S29 真实事故）
[抓到] primary_controller 写成不存在的类名
[抓到] 内层参数另开一个游离块（S29 第二个事故）
[抓到] movement_time_allowance 退回 10s
[抓到] angular_dist_threshold 设成不启用
[抓到] simulate_ahead_time 关闭
[抓到] BaseObstacle.scale 退回官方默认 0.02（S31 爬行事故）
[抓到] robot_radius 顶替 footprint（S32「从下面过不去」事故）      ← 新增
[抓到] 膨胀半径过大，把缝S 重新封死（0.16 → 0.30）                ← 新增
故障注入: 抓到 9 / 漏掉 0
```

> 顺手修了注入器的一个坑：原来只跑 `check_controller.py`，
> 而「车体模型」类故障归 `check_limits.py` 管 ——
> 不跑它，注入进去只会显示「漏掉」，看不出是「该检查却没检查」。
> 现在两个 checker 都跑，任一红就算抓到。

## 六、一句话总结

> 车不是「过不去」，是**代价图认为它过不去**。
> 而代价图认为它过不去，是因为我把一辆 0.30×0.24 的矩形车
> 当成了一个 0.20 半径的圆 —— 凭空胖了 7.2 cm，
> 在 0.655 m 的缝里等于堵死了 14.4 cm。

## 七、教训

1. **「能过」和「代价图允许它过」是两个判据。**
   前者看车宽，后者看 `缝宽 − 2×模型半径`。用错了模型半径，两个判据会打架。

2. **判据必须算「真实对象」，不是「方便的近似」。**
   车心是点，车是矩形。用点代替矩形，在开阔区没差别，在窄缝里差 7.2 cm。

3. **用户的一句方向性描述，胜过十次日志分析。**
   「从上面能过去，从下面卡住」直接把排查范围从「全局/局部/恢复行为」
   收窄到「几何在南北方向上不对称」。**先问现象的方向性，再查代码。**

4. **恢复行为全部失败 = 空间问题，不是控制器问题。**
   spin 失败、backup 失败、wait 也没用 —— 这时不该继续调 critic 权重，
   该去算「车周围还有没有合法格子」。
