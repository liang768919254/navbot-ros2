# S23 建图质量量化：别靠肉眼看 RViz，用数字

日期：2026-11-10
触发：`./drive.py loop` 闭环跑通后，我看 RViz 截图说「墙体外侧有绿色毛边，
SLAM 回环对齐得勉强」，准备去调 `minimum_travel_distance` / `minimum_travel_heading`。

## 结论：地图是准的，不需要改参数

实测（`map_quality.py`，120×100 格，分辨率 0.05 m）：

```
占据   841 格   7.0%
空闲 10890 格  90.8%
未知   269 格   2.2%      ← 判据 < 15%
```

| 墙体 | 内表面真值 | 地图实测 | 偏差 | 检出率 | 判定 |
|---|---|---|---|---|---|
| wall_south | −2.450 | −2.420 | +0.030 | 100% | OK |
| wall_north | +2.450 | +2.480 | +0.030 | 98% | OK |
| wall_west | −2.950 | −2.908 | +0.042 | 98% | OK |

**最大偏差 0.042 m < 1 个栅格（0.05 m）。** 这个精度已经低于栅格分辨率，
继续调 `minimum_travel_distance` 也测不出改善 —— 属于无效优化。

## 绿色激光点贴在外侧是正常的

RViz 里 `Map` 显示占据格（黑色），`LaserScan` 显示本帧命中点（绿色）。
占据格记的是「历史若干帧的光线命中位置」，实时点是「这一帧的命中位置」，
两者本来就该重合或相差一点噪声。**看起来像毛边，其实是两套数据的正常叠加。**

判断建图好坏要看「墙的位置 vs 真值」，不是看截图糊不糊。

## 两次测量方法都错了，而且都错在「真值」

这一轮我改了三次测量方法才得到可信数字。**三次错都不是地图的问题，是基准/算法的问题**，值得记下来。

### 第 1 版：沿法向从远处扫，break 在第一个占据格

```
wall_south  -2.500 → -2.436  (+0.064)  FAIL
wall_west   -3.000 → -2.927  (+0.073)  FAIL
```

**错因**：激光从房间内部打向墙，内表面先被填成占据格。
「第一个占据格」天然偏向房间内侧 → 系统性把墙量薄、量偏。

### 第 2 版：取法向整段连续占据格的 (首+尾)/2

```
wall_south  -2.500 → -2.420  (+0.080)  FAIL   ← 反而更差
wall_west   -3.000 → -2.927  (+0.092)  FAIL
```

**错因**：外墙只有**内表面一侧**能看到，外面是空气，根本没有占据格。
「首尾中点」被硬拉向内侧 0.05 m（半个墙厚），所以比第 1 版还差。

### 第 3 版（正确）：取「离房间最近」的占据格 + 真值改用内表面

```
wall_south  -2.450 → -2.420  (+0.030)  OK
wall_west   -2.950 → -2.908  (+0.042)  OK
```

**两个修正同时生效**：

1. **测量**：`min(occ, key=abs)` —— 房间中心在 (0,0)，绝对值小的那格就是内表面。
2. **真值**：外墙厚 0.1 m 居中在 ±3.0 / ±2.5，所以**内表面 = 中心线 ∓ 0.05**。
   之前拿中心线 −3.00 当真值，而激光永远看不到墙心，
   于是永远量出「偏内半格」的假象。

> 一句话：**激光只能测到它能看到的那一面。拿墙心当真值，测什么都是错的。**

## 顺手确认：雷达的 4 cm 前偏不是问题来源

`base_footprint → laser_link` 实测 `[0.040, 0.000, 0.100]`，
雷达装在车体中心前方 4 cm。

第一反应是「这会不会把地图整体推前 4 cm」。核对后**不会**：
- `slam_toolbox` 用的是 `scan_topic` + TF，会用 `laser_link` 的实际位姿把点云投回 `map` 系
- 所有墙的偏差都是 0.03~0.042 m，**四个方向同号、量级一致**，
  这是栅格量化误差的特征，不是某个方向被整体平移（那只会让两面墙偏差相反）

## 真正值得改的一处（但优先级低）

`minimum_time_interval: 0.5` 而雷达 10 Hz → **每 5 帧只用 1 帧，丢弃 80%**。

当前车速 0.15 m/s，0.5 s 走 7.5 cm，远小于 `minimum_travel_distance` 0.3 m，
所以现在没问题。但跑 Nav2 或提速到 0.3~0.5 m/s 时，
0.5 s 就是 15~25 cm，接近关键帧间距的一半，匹配余量会被吃光。

建议将来提速前改成 `0.2`（5 Hz 处理），仍比关键帧频率高一个量级。
**现在不动** —— 没有证据表明它影响了本次建图质量。

---

## 结论边界

- 只测了**静态位置精度**，没测动态（车在动时地图更新延迟导致的偏差）。
- 检出率 97~100% 是在完整跑完一圈后测的；只跑半圈时覆盖率会低很多。
- 这一轮判断只对 `navbot_room.world` 的 6 条墙成立。换世界必须同步改 `map_quality.py` 的 `WALLS`。
