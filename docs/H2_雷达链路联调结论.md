# H2 · 雷达链路联调结论（2026-10-31 夜）

> 用 `tools/env/check_hw.py --listen --sec 30` 抓到的 R5 扫描固件输出，加上之前存的
> `02_联调工具/raw_ttyUSB0.bin`，把「雷达为什么没数据」定位到了具体一层。

## 一、三层排查结果

| 层 | 检查项 | 结论 | 证据 |
|---|---|---|---|
| ① PC ↔ STM32 | USART1 / CH340 链路 | **✓ 通** | 30 秒收到 6068 字节可读文本，202 B/s |
| ② STM32 的 USART3 配置 | 外设与中断 | **✓ 正常** | `CR1=0x202C`（UE=1 TE=1 RE=1 RXNEIE=1）、`BRR=0x0138`、`NVIC USART3_IRQn=39 enabled=1` |
| ③ STM32 ← 雷达 | 实际收到的字节 | **✗ 全空** | `rx=0 B`、`points=0`、`HEAD: <none>`、`resync=0` |

**问题在第 ③ 层，也就是雷达那侧。软件全部正常。**

## 二、为什么能确定是雷达侧

R5 固件自己打印的统计是硬证据（三轮扫描全一样）：

```
CHANNEL rx=0 B  overflow=0  points=0  resync=0
HEAD: <none>
```

四个字段连起来读：

| 字段 | 值 | 含义 |
|---|---|---|
| `rx` | 0 B | USART3 **一个字节都没收到** |
| `resync` | 0 | 连「错误帧头」都没有——不是收到了乱码，是彻底没有信号 |
| `HEAD` | `<none>` | 从来没匹配到 RPLIDAR 的 `0x5A 0xA5` 帧头 |
| `points` | 0 | 因此一个点都没解出来 |

如果只是**波特率不匹配**，`rx` 会有值、`resync` 会不停累加。
`rx=0` + `resync=0` 同时成立，只能是「线路上没有任何电平变化」。

顺带排除了配置层：`BRR=0x0138` 反算波特率 = 36 MHz / 312 = **115384 ≈ 115200**，
和 RPLIDAR A1 的默认波特率一致，这一项是对的。

## 三、固件自检的两处判据缺陷

固件有 T1–T6 六项判据，三轮结果都是 `1/6 PASS`：

```
[FAIL] T1 pose samples      0 0 0 0 0 (need >= 2000 each)
[FAIL] T2 sector cover      0/72 = 0.0% (need >= 90.0%)
[FAIL] T3 world span        0.0 deg (need >= 350.0)
[FAIL] T4 sector spread     0.0% over 0 sectors (need <= 10.0%)
[FAIL] T5 valid echoes      0.0% (need >= 30.0%)
[PASS] T6 no rx overflow    0 (need 0)
```

**缺陷一：T1 失败时给的提示是误导的**

`radar_scan.c:343-349` 里 T1 失败固定打印：

```
T1 fail -> a pose got too few points. look at:
  a) servo didn't reach the angle (power? 5V rail? horn loose?)
  b) SCAN_SERVO_ENABLE=1 but SG90 not wired to PA8/H1
  c) that pose window lost bytes (check T6 first)
```

三条全部假设「雷达有数据、只是点少」。但实际是 `rx=0`——一个字节都没有。
更矛盾的是 `SCAN_SERVO_ENABLE = 0`，**舵机压根没初始化**，a) 和 b) 根本不可能成立。
c) 又因为 T6 是 PASS 被排除。**三条提示全部走不通，只会把人往舵机上引。**

> 判据顺序应该是：先查 `rx == 0`（有没有数据）→ 再查 `HEAD`（帧头对不对）→
> 最后才谈 points 少（这时舵机、遮挡才成为候选）。
> 「没数据」和「数据不够」是两类完全不同的故障，不能共用一套提示。

**缺陷二：T6 的 PASS 是假阳性**

`overflow == 0` 在 `rx == 0` 时必然成立——没有数据可溢出。
这给了一个「1/6 PASS」的假象，好像还有一项是好的。
`rx == 0` 时 T6 应该标 `N/A`（未验证），不要计入通过项。

## 四、下一步查什么（按概率排序）

| # | 检查 | 怎么查 | 典型现象 |
|---|---|---|---|
| 1 | **雷达有没有供电** | 上电后 A1 的转盘**会转**。不转就是没供电 | 转盘静止 = 供电问题，先查 5V |
| 2 | **TX 线接对没有** | 雷达 TX → STM32 **PB11**（USART3_RX）。串口是**交叉接** | 接成 TX→TX 就是 `rx=0` 的典型表现 |
| 3 | 共地 | 雷达 GND 必须和 STM32 GND 连上 | 不共地时电平参考漂移，也是收不到 |
| 4 | 雷达本身好坏 | 把雷达接到 USB 转接板（CP210x）用官方工具试 | 能出点 = 雷达好的，问题在接线 |

**第 1 条和第 2 条加起来能覆盖 90% 的 `rx=0`。**
先看转盘转不转（眼睛就行），再量 PB11 到雷达 TX 是否导通（万用表通断档）。
交叉接错是「一行代码都没问题但就是没数据」的头号原因。

## 五、当前固件状态（R5 SCAN）

```
R5 SCAN  --  RPLIDAR A1 (USART3) + SG90 (TIM1_CH1/PA8)
sectors = 72 x 5 deg, poses = 5, dwell = 1500 ms
world_q6 = servo*64 + lidar_q6  (mod 360)
SCAN_SERVO_ENABLE = 0 -> servo stays still, all poses treated as 0 deg
```

两个配置项值得注意：

- `SCAN_SERVO_ENABLE = 0` → 舵机不初始化。5 个 pose 全部按 0° 处理，
  等于只扫一个固定角度。等雷达通了再打开它才是真正的三维扫描。
- 一轮扫描 = 5 pose × (1500 ms 稳定 + 1500 ms 采集) = **15 秒**，
  和「30 秒内 banner 出现两次」完全对得上——不是复位，是每轮重新打印一次。

## 六、判据修正（这次踩到的）

之前脚本的「雷达链路」按「有没有 CP210x/FT232」判断，对这块板是错的：
**雷达直接接 STM32 的 USART3（PB10/PB11），根本不经过 USB**，Linux 侧永远看不到它。

已改成三态：

| 情况 | 判定 |
|---|---|
| 找到 CP210x/FT232 | ✓ 雷达走 USB 转接板 |
| 只有 MCU 调试口 | **? 待确认**——可能接在 MCU 的 UART 上，Linux 侧不可见 |
| 什么都没有 | ✗ |

`--strict` 只对明确的 ✗ 返回 1，「待确认」不算失败——否则门禁会被不可见项卡死。
