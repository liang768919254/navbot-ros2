# S26 复盘：地图质检的三个方法坑

> 日期：2026-11-10
> 触发：`map_quality.py` 里 `partition_stub` 那条一直报 FAIL，偏差 +0.175 m
> 结论：**地图没问题，是质检方法错了三次；而且连「被测对象的形状」都搞错了**

---

## 一句话结论

`map_quality.py` 原来 6/7 OK、1 条 FAIL。修完之后 7/7 全 OK。
但中间踩了三个坑，每一个都指向同一条教训：

> **测量工具的错误，看起来永远像被测对象的错误。**

---

## 坑 1：把「独立方块」交给「逐墙法向扫描」量

### 现象

```
partition_stub   -1.595   -1.420   +0.175   83%   FAIL
```

偏差 0.175 m = 3.5 个栅格，远超 1 格判据。第一反应是「建图不准」。

### 真相

剖开看，stub 在 `x=-1.88` 处的竖直剖面：占据格 `y∈[-1.745, -1.445]`，
**包围盒中心 -1.595，与真值偏差 0.000**。

那 0.175 是哪来的？`measure_wall()` 的判据是：

> 沿法向找到所有占据格，取**离房间中心 (0,0) 最近**的那一个。

这条判据是为**外墙**量身定做的——激光只能打到墙的内表面，外面是空的，
所以「最近的那个格」= 内表面，正是我们要的。

但 stub 是**独立小块，四侧都是通路**。「离房间中心最近」对它毫无意义：
从 y=0 往下扫，第一个撞上的是 stub 的**上沿** -1.445，不是中心。
于是量出来的是「上表面位置」而不是「中心位置」，差半个尺寸 0.175 = 0.35/2。

### 修正

给「两侧都可见的独立物体」单开一类测量：穷举搜索矩形内全部占据格，
取 `min/max` 求包围盒中心。

```python
def measure_box(g, name, cx, cy, x0, x1, y0, y1):
    xs, ys = [], []
    # 穷举该矩形内的占据格
    bx = (min(xs) + max(xs)) / 2.0
    by = (min(ys) + max(ys)) / 2.0
    dev = max(abs(bx - cx), abs(by - cy))   # 两个轴都得对
```

### 提炼

> **判据要和被测对象的可见性匹配。**
> 只有一侧可见 → 取表面；四侧都可见 → 取包围盒中心。
> 同一套方法套所有对象，一定有一条是错的。

## 坑 2：`--offline` 读 PGM 忘了从 yaml 取原点

### 现象

为了不启 ROS 也能复算判据，加了 `--offline <pgm>`。跑出来的结果是：

```
wall_north     2.450   2.035   -0.415   39%  FAIL
wall_west     -2.950  -2.475   +0.475    1%  FAIL
partition_mid  0.505  未检出      -      0%  FAIL
```

全军覆没，看起来像地图彻底坏了。

### 真相

`load_pgm()` 的默认原点是 `(-3.1, -5.49)`（那是我写函数时随手填的旧值）。
而 `navbot_room.yaml` 里的真实原点是 `(-2.983, -2.495)`。

**y 方向差了 3 米**，整张地图在世界坐标系里整体平移，
所以「每条墙都偏、而且偏得很离谱」。

### 修正

```python
res, ox, oy = _read_yaml(pgm_path)   # 从同名 yaml 读 resolution / origin
m = load_pgm(pgm, res, ox, oy)
```

### 提炼

> **地图的世界坐标由 `origin` 决定，不由像素决定。**
> 任何「整张图每条墙都偏同一个量」的现象，第一嫌疑是原点错，不是建图错。
> 这条和 S25 的「PGM 行序陷阱」是一对兄弟：一个管上下颠倒，一个管整体平移。

## 坑 3（最严重）：`partition_stub` 根本不是方板，是圆柱

### 现象

修完前两个坑，7/7 都 OK 了。但打印出来的尺寸对不上：

```
真值尺寸 0.30×0.30     实测 0.35×0.35
```

`0.35 = 0.30 + 0.05`，正好是一个栅格。我一度以为又是量化误差。

### 真相

翻 `navbot_room.world` 才发现：**整个项目里就没有 `partition_stub` 这个模型。**

```xml
<model name="pillar_b">
  <pose>-1.9 -1.6 0.25 0 0 0</pose>
  <geometry><cylinder><radius>0.15</radius><length>0.5</length></cylinder></geometry>
</model>
```

它是**半径 0.15 的圆柱**，不是方板。而圆柱在 5cm 栅格上的外接框必然是
`2r + 1 格 = 0.30 + 0.05 = 0.35` 见方——这是**栅格化的必然结果**，不是误差。

也就是说：
- 「边长 0.35」这个数，用包围盒法量出来永远是 `2r + 1格`，永远对不上 `2r`
- 更糟的是，如果拿 0.35 当矩形去算净空，会**系统性把柱子算粗半格**，
  把本来能走的通道判成死路

顺带发现 `pillar_a` 在 `(1.8, 1.5)`、半径同样 0.15，**从来没进过任何自测**。

### 修正

`room_geom.py` 里把「方板」改成对象元数据：

```python
PILLAR_B = dict(name='pillar_b', cx=-1.9, cy=-1.6, r=0.15)
PILLAR_A = dict(name='pillar_a', cx=1.8,  cy=1.5,  r=0.15)

def pillar_passage(p=PILLAR_B):
    """绕立柱的可行车心 x 区间（距**柱面**至少 robot_radius）"""
    return X_MIN + ROBOT_RADIUS, p['cx'] - p['r'] - ROBOT_RADIUS
```

注意用柱面 `cx - r` 而不是外接框左边 `cx - r - 半格`，
否则白白多留 0.025 m，把本来能过的通道判死。

自测里也补了一条形状校验，并把写死的数字换成恒等式：

```python
# 旧：chk(abs(hi - (-2.233)) < 1e-9, ...)          ← 写死，改几何就挂
# 新：chk(abs(hi - (PILLAR_B['cx'] - PILLAR_B['r'] - ROBOT_RADIUS)) < 1e-9, ...)
```

### 提炼

> **包围盒只能告诉你「占了多少格」，不能告诉你「是什么形状」。**
> 形状必须回 `world` / `urdf` / 建模源文件查，**不能从栅格数据反推**。
>
> 更要命的是：圆柱、球这类曲面物体，栅格化后外包框**永远**比真实尺寸大 1 格。
> 拿外包框当真实尺寸做净空计算，是「差一格级」的系统性保守错误，
> 在小通道（0.45 m 缝）上足以改变能不能过的判断。

## 附带修掉的一个架构问题：真值有两份副本

### 现象

`map_quality.py` 的 `WALLS` 是**手抄**的一份真值，
`room_geom.py` 的 `PARTITIONS` 是另一份。两边各改各的版本。

S25 复盘里 `PARTITIONS` 改了三次，但 `map_quality.py` 里还是旧的，
于是一直 FAIL 却查不出原因——因为我以为「真值已经修好了」。

### 修正

`map_quality.py` 改成从 `room_geom` 派生：

```python
import room_geom as RG

def _derive_truth():
    walls = [
        ('wall_south', 'h', RG.Y_MIN, RG.X_MIN, RG.X_MAX, RG.WALL_T),
        ...
    ]
    for name, kind, x0, x1, y0, y1 in RG.PARTITIONS:
        if max(x1-x0, y1-y0) <= 0.45:
            boxes.append(...)       # 独立物体 → 包围盒中心校验
        else:
            walls.append(...)       # 长条隔板 → 逐墙法向扫描
    return walls, boxes

WALLS, BOXES = _derive_truth()
```

顺带把「板 / 块」的分类判据改对：原来用 `min(dx,dy) <= 0.40`，
会把 `0.25×1.80` 的 `partition_short` 也判成方块（因为 0.25 ≤ 0.40）。
改成 `max(dx,dy) <= 0.45`——必须**两个方向都短**才算独立物体。

### 提炼

> **凡是「算错了就撞墙」的数字，只允许有一个来源。**
> 第二份手抄副本不是冗余，是定时炸弹：它会在未来某次修改后
> 以「明明改好了却还报错」的形式诈你一轮。

## 检查清单（下次改地图/几何先过一遍）

| # | 检查项 | 怎么查 |
|---|--------|--------|
| 1 | 对象的**形状**是什么？ | 回 `world` / `urdf` 查，别看栅格反推 |
| 2 | 是曲面吗？外包框 = 真实 + 1 格 | 圆柱/球必须用 `2r` 而不是 `2r+res` 算净空 |
| 3 | 这个对象几侧可见？ | 1 侧 → 取表面；4 侧 → 取包围盒中心 |
| 4 | 地图原点从哪来？ | 必须读 yaml 的 `origin`，不能用默认值 |
| 5 | PGM 行序翻了吗？ | 自顶向下读，栅格自底向上存 |
| 6 | 真值有几份副本？ | 只能有一份，其余全部 import |
| 7 | 自测里的期望值写死了吗？ | 能写成恒等式就不要写常数 |

# 附录：RViz 里只剩一张网格、中间一个白方块

> 2026-11-10 18:40 小梁同学截图报的现象
> 结论：**地图没丢，是 `map→odom` 这条链断了**——`map_server` 没 active

## 现象

RViz 打开 `navbot_nav.rviz`，屏幕上是：

- 一片深灰背景
- 几条灰色网格线
- **正中间一个白色小方块**

没有任何墙体、没有激光点、没有车模。

第一反应很容易是「地图文件坏了」或「RViz 配置改坏了」。
**两者都不是。**

## 一分钟定位法

```bash
timeout 8 ros2 lifecycle get /map_server      # inactive [2]
timeout 8 ros2 lifecycle get /amcl            # unconfigured [1]
timeout 6 ros2 topic hz /map                  # 无输出（没发布）
grep '\[amcl' live_nav.log | tail -3
# AMCL cannot publish a pose or update the transform. Please set the initial pose...
```

四条一对照，因果链就出来了：

```
map_server 没 activate
      ↓
/map 上没有数据
      ↓
AMCL 收不到地图 → 一直等初始位姿 → 不发布 map→odom
      ↓
TF 树里没有 map 帧
      ↓
global_costmap 刷屏 "Invalid frame ID map ... frame does not exist"
RViz 的 Fixed Frame 是 map，解析失败 → 只能画出 Grid，其余全部不显示
```

那个白色方块就是 **Grid 的中心小块**，不是地图内容，也不是机器人。
Grid 是唯一不依赖 TF 的显示项，所以只剩它还在。

## 为什么 map_server 没被激活

`live.sh nav` 原来是这个时序：

```bash
ros2 launch nav_bringup.launch.py ... &
sleep 12                                    # ← 硬赌 Nav2 12 秒起得来
python3 odom_pose.py                        # 读 odom
python3 set_pose.py "$PX" "$PY" "$QW" "$QZ" # 发初值，发完不管
```

两个问题：

1. **`sleep 12` 是赌注。** 机器忙（尤其第一次加载地图 + 一堆节点抢 CPU）时
   12 秒不够，`set_pose.py` 发出的 `/initialpose` 直接丢进真空。
2. **发完不验证。** 初值到底有没有生效，脚本完全不知道，一路往下走。

而 Nav2 的 lifecycle manager 又是**串行激活**的：`map_server` 卡在
configure 没 activate，后面的 `amcl`、`planner_server` 全排队等着，
连锁反应一直传到 RViz。

## 修法

`live.sh nav` 改成三段式，每段都有明确的成功判据：

```bash
# ① 等 map_server active（最多 60s），并打印实际等了几轮
# ② 发初值
# ③ 等 map->odom 出现（最多 20s）；没出现就重发一次，仍失败则打印诊断命令
```

判据用的是**观测到的状态**，不是时间：

| 阶段 | 判据 | 不合规时 |
|------|------|---------|
| map_server | `ros2 lifecycle get /map_server` 含 `active` | 打印日志查看命令，指出 yaml 路径/PGM 头两个常见原因 |
| AMCL 初值 | `tf2_echo map odom` 输出含 `Translation` | 自动重发一次；再失败打印 amcl 日志过滤命令 |

`nav_precheck.py` 的 TF 检查也同步改了：原来失败一律提示
「slam_toolbox 还在跑？」，现在按情况分岔——

- 没有 `/map` → 「map_server 没 active」
- 有 `/map` 但没 `map→odom` → 「**初始位姿没发进去**」（AMCL 会喊 Please set the initial pose）

## 手动救活的方法（不改任何文件）

如果已经掉进这个坑，三步拉回来：

```bash
# 1. 手动激活 map_server
ros2 lifecycle set /map_server activate

# 2. 激活 AMCL
ros2 lifecycle set /amcl configure
ros2 lifecycle set /amcl activate

# 3. 按实测 odom 位姿注入初值（★ 这一步是解开死锁的钥匙）
cd ~/navbot_ws/tools/verify/sim_fullchain
read PX PY QW QZ <<< "$(python3 odom_pose.py)"
python3 set_pose.py "$PX" "$PY" "$QW" "$QZ"
```

`map→odom` 一出现，**lifecycle manager 会自动把剩下的
`planner_server` / `bt_navigator` / `behavior_server` / `waypoint_follower`
依次激活**（实测 4 秒内全部变 active）。不用手动一个个点。

## 提炼

> **RViz 只显示网格 = Fixed Frame 解析失败。**
> 这时不要去查地图文件、不要去改 rviz 配置，直接查目标帧在不在 TF 树里。
>
> **生命周期的错误会伪装成完全无关的症状。**
> 一个 `map_server` 没 activate，表现是「地图丢了」「障碍物没了」「RViz 一片空白」。
> 排查顺序永远是：**先看 lifecycle，再看 topic，最后才看 RViz。**
