## 三、根因：`primary_controller` 填的是类名，不是参数块名

我 S28 写的时候是这么想的：

> 外层叫 `FollowPath`，内层叫 `FollowPathDWB`，`primary_controller: "FollowPathDWB"`，
> 两个名字必须不同，否则 shim 会把自己当内层、无限递归。

**前半句对，后半句理解错了对象。** `primary_controller` 不是「去哪个参数块找」，
是「用哪个 pluginlib 类来实例化」。

去源码里看（`nav2_rotation_shim_controller.cpp`）：

```cpp
primary_controller = node->get_parameter(plugin_name_ + ".primary_controller").as_string();

primary_controller_ = lp_loader_.createUniqueInstance(primary_controller);
//                   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 按【类名】加载
//                   lp_loader_ 是 pluginlib::ClassLoader<nav2_core::Controller>

primary_controller_->configure(parent, name, tf, costmap_ros);
//                              ^^^^ 这是 shim 自己的 plugin_name（= "FollowPath"）
```

两行代码，两个独立的语义：

| 参数 | 用途 | 正确值 |
|---|---|---|
| `primary_controller` | pluginlib **类名** | `"dwb_core::DWBLocalPlanner"` |
| `configure(parent, name, ...)` 的 `name` | 内层读参数的**前缀** | shim 自己的 `plugin_name`（`"FollowPath"`） |

⇒ **推论**：内层 DWB 的参数必须写在 `FollowPath:` 块下，
我自己另开的 `FollowPathDWB:` 块**从头到尾没有任何人读过**。

这是我犯的第二个错，而且更阴险——它**不报错**。如果只修 `primary_controller` 的类名，
仿真能起来，但 DWB 会全用默认值（`max_vel_x` 0.26 而不是 0.22），表现是「能走但比预期快、比预期飘」，
又要多花几轮才能查到。

## 四、更严重的问题：我的检查脚本把错的当成了对的

S28 建的 `check_controller.py` 是全绿的 9/9。它当时是这么判断的：

```python
elif inner not in cs:
    ng('primary_controller = %r，但 yaml 里没有这个参数块' % inner)
else:
    ok('primary_controller = %r 存在且不自指' % inner)
```

**逻辑写反了方向**。它查的是「`cs` 里有没有这个 key」，而 `cs` 是我自己写的字典——
我自己起的名字，当然查得到。这等于「用自己的答案核对题目」。

对照 `MIN_ALLOWANCE_FOR_ROTATE` 那次教训（S28 第九节第④条）：
那次是**阈值太松**，改个数就行；这次是**检查对象错了**，必须换判据。

### 新判据：到 .so 里查类名是否真实存在

```python
# 从 pluginlib 的 .so 里抠出所有导出的类名
def find_plugin_classes(plugins_dir):
    found = set()
    for lib in glob.glob(os.path.join(plugins_dir, 'lib*.so')):
        out = subprocess.run(['strings', lib], capture_output=True, text=True).stdout
        for m in re.finditer(r'\b((?:nav2|dwb)_[a-z0-9_]*::[A-Za-z0-9_]+)\b', out):
            found.add(m.group(1))
    return found

# 判据
classes = find_plugin_classes('/opt/ros/humble/lib')
if inner_cls in classes:
    ok('类名 %s 在 .so 中确实存在' % inner_cls)
else:
    ng('类名 %r 在任何 .so 中都找不到 —— controller_server 会 FATAL 后 SIGSEGV')
```

**这是「问系统，不是问自己」**。yaml 里的名字可以任意编，`pluginlib` 声明表不能。

### 第二条新判据：抓「游离的参数块」

```python
# 先算出哪些块是「有自己引用入口的合法子插件」
referenced = set()
if isinstance(cs.get('progress_checker_plugin'), str):
    referenced.add(cs['progress_checker_plugin'])
referenced.update(cs.get('goal_checker_plugins') or [])

# 剩下的、plugin 又是 dwb/shim 的块 = 没人读
for key, val in cs.items():
    if key == entry or key in referenced:
        continue
    if 'dwb' in val.get('plugin','').lower():
        ng('存在无人读取的控制器参数块 %r' % key)
```

> ★ 这条筛子第一次写的时候漏了 `referenced`，把 `progress_checker` 和
> `general_goal_checker` 误报成「游离块」，一次冒出 4 条假 FAIL。
> 误报比漏报更坏 —— 会让人开始忽略检查结果。

## 五、修法

### 5.1 参数归位

| 项 | 改前（错） | 改后 |
|---|---|---|
| `primary_controller` | `"FollowPathDWB"` | `"dwb_core::DWBLocalPlanner"` |
| DWB 速度/采样参数 | 独立 `FollowPathDWB:` 块 | **全部移进 `FollowPath:`** |
| `rotate_to_heading_when_stopped` | `true` | **删除**（Humble 无此参数） |
| 新增 | — | `simulate_ahead_time: 1.0` |
| 新增 | — | `forward_sampling_distance: 0.5` |
| 新增 | — | `angular_disengage_threshold: 0.5` |

改完 `FollowPath` 从 7 个键变成 47 个键（shim 的 10 项 + DWB 的 37 项），
`general_goal_checker` 回到 4 个键。

### 5.2 `rotate_to_heading_when_stopped` 是我编的

`.so` 字符串扫描结果：

```
.angular_dist_threshold   .maximum_angular_accel → .max_angular_accel
.simulate_ahead_time      .closed_loop
.primary_controller       .rotate_to_heading_angular_vel
```

**没有 `rotate_to_heading_when_stopped`**。源码 `configure()` 里也只是用
`declare_parameter_if_not_declared` 声明的 9 个，没有它。

那「原地转」怎么保证的？看 `computeRotateToHeadingCommand()`：

```cpp
geometry_msgs::msg::TwistStamped cmd_vel;
cmd_vel.header = pose.header;
cmd_vel.twist.angular.z = std::clamp(angular_vel, min_feasible, max_feasible);
// ↑ 只填了 angular.z，linear 从头到尾没赋值 → 保持初始化的 0 值
```

**TwistStamped 默认零初始化，linear 恒为 0 ⇒ 天然就是原地转。**
这个开关是 Jazzy+ 才加的，Humble 里根本没有，「边转边走」在 Humble 不会发生。

> 教训：**参数名不能凭印象写**。哪怕它「听起来非常合理」，
> 也要么 `strings` 扫 `.so`，要么翻源码，二选一。

## 七、改 yaml 结构踩的三个坑（工具层面）

这次要把一个 98 行的块从 `general_goal_checker` 里搬出来、塞进 `FollowPath`，
我用脚本操作文本，连错三次：

| 错误 | 症状 | 原因 |
|---|---|---|
| ① 缩进剥多了 | 参数从「在块内」变成「在块外」 | 我 `l[2:]` 去掉了 2 个空格，6→4，正好掉出 `FollowPath` 的子级 |
| ② 块结束判定错 | 参数挂到了 `general_goal_checker` 下（40 键） | 我把「缩进 ≤ 4 的非空行」当块尾，但 `general_goal_checker:` 本身就是 4 格缩进，`FollowPath` 和它同级 |
| ③ `/tmp` 不共享 | 提取的中间文件下一次调用就没了 | 本机 Bash 每次调用 `/tmp` 独立（老问题） |

**正确姿势**（最后用的）：

1. 不在两次调用间传文件，**一次 `python3 -` heredoc 里做完**
2. 不猜块边界，用「**找具体锚点字符串**」而不是「看缩进」——
   锚点 = `yaw_goal_tolerance` 行 到 `local_costmap:` 行
3. 每步之后**用 `yaml.safe_load` 打印每个块的键数**，键数不对立刻停


## 九、教训

1. **`primary_controller` 是类名，不是参数块名。**
   内层参数前缀 = 外层 `plugin_name`，不是内层块名。

2. **检查脚本也可能写错方向。**
   「yaml 里有没有这个 key」是自己核对自己；
   「`.so` 里有没有这个类」才是问系统。

3. **误报比漏报更坏。**
   新的「游离块」判据第一版误报 4 条，会让人开始无视检查结果。
   写判据时先问：**哪些是正常的？** 把它们显式排除掉。

4. **参数名一律查，不凭印象。**
   `rotate_to_heading_when_stopped` 听起来天经地义，Humble 里不存在。

5. **`FATAL` 之后不一定停下。**
   nav2 的 `configure()` catch 异常后只 `return`，留下 `nullptr`，
   崩溃推迟到 `activate()`。看到 FATAL 就该当致命处理，别等 SIGSEGV。

6. **改 yaml 结构后立刻查键数。**
   键数是结构正确性最快的指标，比肉眼读缩进可靠得多。
