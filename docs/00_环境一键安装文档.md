> **适用环境**：Ubuntu 22.04 LTS（Jammy）

## 0.1 ★ `ros2 pkg list | wc -l` 该是多少？（实测基准，别被"300+"误导）

| 环境 | 包数 | 说明 |
|---|---|---|
| **`setup_env.sh` 装完（本项目）** | **211** | 只装导航栈必需的包 |
| `ros-humble-desktop` 全套 | 300+ | 含 turtlebot 演示、诊断工具、大量示例 |

> ★ **211 就对了，不必追求 300+**。文档早前写的"应 300+"是 desktop 全套的基准，
> 而本项目是按需装包（`setup_env.sh` 装 20 个直接依赖 + 它们的传递依赖）。
> 多出来的 100 来个包对导航演示**没有作用**，反而占磁盘。

**本项目实际需要的 20 个包**（已逐个核对源里都有）：

| 类别 | 包 |
|---|---|
| CLI | `ros2cli`、`ros2cli-common-extensions`（带 run/topic/node/service/action/lifecycle/launch 等 15 个子命令） |
| 建模 | `xacro`、`urdf` |
| 状态发布 | `robot-state-publisher`、`joint-state-publisher`、`joint-state-publisher-gui` |
| TF/可视化 | `tf2-tools`、`rviz2` |
| 导航 | `navigation2`、`nav2-bringup`、`nav2-rviz-plugins`、`nav2-simple-commander` |
| SLAM | `slam-toolbox` |
| 仿真 | `gazebo`（Ubuntu 源）、`gazebo-ros-pkgs` |
| 控制 | `twist-mux`、`teleop-twist-keyboard` |
| 构建 | `ament-cmake`、`ament-lint-auto` |

**判断环境是否够用，别看包数，看这三条**：

```bash
ros2 pkg list | grep -cE 'nav2_bringup|slam_toolbox|gazebo_ros|rviz2'   # 应 ≥ 4
ros2 run tf2_ros tf2_echo   # 能跑就说明 tf2_ros 在（★ 注意是 tf2_ros 不是 tf2_tools）
ros2 launch navbot_bringup sim_navbot.launch.py    # 能起就说明依赖齐
```

> ⚠️ **tf2 命令速查（包名很容易记混，实测踩过）**：
>
> | 命令 | 属于哪个包 |
> |---|---|
> | `ros2 run tf2_ros tf2_echo` | **tf2_ros** |
> | `ros2 run tf2_ros tf2_monitor` | **tf2_ros** |
> | `ros2 run tf2_ros static_transform_publisher` | **tf2_ros** |
> | `ros2 run tf2_tools view_frames` | **tf2_tools**（只出 PDF 树图） |
>
> ⇒ `tf2_tools` 里**没有** `tf2_echo`，写错会报 `No executable found`。
> 记忆法：**"echo/查数值" 都在 `tf2_ros`，只有"出图"才在 `tf2_tools`**。

> ⚠️ **包名用连字符，不是下划线**：`ros-humble-joint-state-publisher` ✅
> 而 `ros-humble-joint_state_publisher` ❌ 装不到。写 apt 命令时别混。

## 1. 一键安装脚本（完整版）

> ⚠️ **本节是"通用完整版"（给新机器/换系统用）**。
> **魔搭实例日常请直接跑项目自带的 `bash setup_env.sh`** —— 它针对国内网络和
> 魔搭环境做了适配（ROS2 源、密钥权限、rosdep镜像、gpu_ray→ray 等），
> 比下面这份通用脚本稳得多。

> 直接整段复制到终端执行。已装过的包 apt 会自动跳过，重复执行无副作用。
> fishros 那一步需要交互，**请选 desktop 版**（不要选 base，否则没有 rviz2）。

```bash
#!/usr/bin/env bash
set -e

# ============ 阶段 0：基础工具 ============
sudo apt update
sudo apt install -y \
  build-essential git cmake curl wget \
  python3-pip python3-argcomplete

# ============ 阶段 1：ROS2 Humble（fishros 一键，选 desktop）============
wget http://fishros.com/install -O fishros && . fishros

# ============ 阶段 2：构建与依赖工具链 ============
sudo apt install -y \
  python3-colcon-common-extensions \
  python3-rosdep \
  python3-vcstool

# ---- rosdep 初始化 + 国内镜像加速 ----
# ★ 国内必做：raw.githubusercontent.com 连不上，rosdistro 索引走中科大镜像
sudo rosdep init || true          # 已 init 过会报 "already exists"，忽略即可
sudo rosdep fix-permissions       # 若之前用 sudo 跑过 update，先修权限
export ROSDISTRO_INDEX_URL=https://mirrors.ustc.edu.cn/rosdistro/index-v4.yaml
echo 'export ROSDISTRO_INDEX_URL=https://mirrors.ustc.edu.cn/rosdistro/index-v4.yaml' >> ~/.bashrc
rosdep update                     # ★ 不加 sudo，普通用户跑

# ============ 阶段 3：机器人建模与状态发布 ============
sudo apt install -y \
  ros-humble-xacro \
  ros-humble-urdf \
  ros-humble-robot-state-publisher \
  ros-humble-joint-state-publisher \
  ros-humble-joint-state-publisher-gui \
  ros-humble-tf2-tools \
  ros-humble-rviz2

# ============ 阶段 4：Nav2 完整导航栈 ============
# navigation2 是总元包，会连带 amcl / dwb-controller / navfn-planner / map_server 等
sudo apt install -y \
  ros-humble-navigation2 \
  ros-humble-nav2-bringup \
  ros-humble-nav2-rviz-plugins \
  ros-humble-nav2-simple-commander

# ============ 阶段 5：SLAM ============
sudo apt install -y ros-humble-slam-toolbox

# ============ 阶段 6：Gazebo Classic 仿真 ============
# ★ 注意：装的是 Classic 11，不是 Ignition/Garden（那个是 ros-humble-ros-gz）
sudo apt install -y \
  gazebo \
  ros-humble-gazebo-ros-pkgs

# ============ 阶段 7：运动控制与多源仲裁 ============
sudo apt install -y \
  ros-humble-twist-mux \
  ros-humble-teleop-twist-keyboard

# ============ 阶段 8：定位与传感器（真机用，无硬件可先跳过）============
sudo apt install -y \
  ros-humble-robot-localization \
  ros-humble-rplidar-ros

# ============ 阶段 9：串口 / 无硬件自测工具链 ============
# ★ pyserial 必须用 apt 的 python3-serial，不要用 pip install pyserial
sudo apt install -y \
  socat \
  python3-serial

# ============ 阶段 10：可选参考（备用）============
sudo apt install -y \
  ros-humble-turtlebot3-gazebo \
  ros-humble-urdf-tutorial

echo "===== 全部安装完成 ====="
```

## 4. 常见坑（本项目的踩坑记录）

1. **Gazebo 版本**：Humble 对应 **Gazebo Classic 11**，包名就是 `gazebo`。不要装 `ros-humble-ros-gz`（那是新 Gazebo Ignition/Garden 的桥接），否则 `navbot.gazebo.xacro` 里 `<gazebo>` 标签的插件会找不到。

2. **pyserial 必须用 apt**：`sudo apt install python3-serial`，**不要** `pip install pyserial`。本项目 `fake_chassis.py` 用的是系统 python（`/usr/bin/python3`），pip 装的环境不一定是系统环境。

3. **fishros 选 desktop**：选 base 版会缺 rviz2、turtlebot3 演示等，导航项目用 desktop 省事。

4. **`source setup.bash` 在 `set -u` 脚本里报错**：`/opt/ros/humble/setup.bash` 内部引用了未定义变量（`AMENT_TRACE_SETUP_FILES` 等），在 `set -u` 下 source 会报 `未绑定的变量`。解法是 source 前后临时 `set +u` / `set -u`（本项目 `verify_e2e.sh` 就是这么处理的）。

5. **虚拟串口依赖 pty**：`socat pty` 依赖 `/dev/ptmx` 和 `/dev/pts`，容器/部分 WSL/安全沙箱里会缺，报 `openpty(...): No such file or directory`。本项目脚本已内置 TCP 回环降级路径，真机 Ubuntu 双系统上不会遇到。

6. **rosdep 未 init**：`colcon build` 若报 rosdep 相关错误，先 `sudo rosdep init && rosdep update`。

7. **`rosdep update` 卡在 `raw.githubusercontent.com` 超时**：国内连不上，报 `error loading sources list: The read operation timed out`（本坑已实测复现，raw 返回 000）。解法是让 rosdistro 索引走中科大镜像：
   ```bash
   export ROSDISTRO_INDEX_URL=https://mirrors.ustc.edu.cn/rosdistro/index-v4.yaml
   rosdep update
   ```
   并写入 `~/.bashrc` 持久化（下次换环境也不用再设）。两点注意：
   - `20-default.list already exists` 不是错误，说明 `rosdep init` 已做过，跳过即可；
   - 若之前用 `sudo rosdep update` 跑过（提示 `running as root is not recommended`），先 `sudo rosdep fix-permissions`，再用**普通用户**（不加 sudo）跑 `rosdep update`。

8. **`colcon build` 报 `find_package(joint_state_publisher)` 找不到 Config.cmake**：`joint_state_publisher` 是**纯 Python 包**（ament_python），不提供 `joint_state_publisherConfig.cmake`，所以在 ament_cmake 包里的 `find_package(joint_state_publisher REQUIRED)` 必然失败（本坑已实测复现）。报错形如：
   ```
   Could not find a package configuration file provided by "joint_state_publisher"
   ```
   解法：把 `joint_state_publisher`（以及 `robot_state_publisher`）从**编译依赖**降为**运行时依赖**：
   - `CMakeLists.txt` 删掉 `find_package(joint_state_publisher REQUIRED)`（`robot_state_publisher` 同理可删）；
   - `package.xml` 把 `<depend>` 改成 `<exec_depend>`。
   
   根因是 `ros2 pkg create --dependencies ... joint_state_publisher` 把运行时依赖写进了 `--dependencies`，导致生成了错误的 `find_package`。正确做法：`--dependencies` 只放有 Config.cmake 的包（urdf/xacro），运行时用的节点（joint_state_publisher / robot_state_publisher）放到 `<exec_depend>`。

9. **「E: 无法定位软件包 ros-humble-*」（本项目实测，魔搭实例重置后必现）**：
   `setup_env.sh` 一度在 `[1/6]` 直接 `apt install ros-humble-*`，但整个脚本里**没有任何一步去添加 ROS 2 的 apt 源**。实例重置后 `/etc/apt/sources.list.d/` 被清空，apt 只看得到 Ubuntu 官方源，于是所有 `ros-humble-*` 全部定位失败。

   ★ **容易误判成「包名写错了」，其实不是**。报错里那三个 python 包看着更可疑，但它们的名字是对的，只是**只存在于 ROS 2 源**：
   | 包名 | Ubuntu 22.04 官方源 | ROS 2 源 |
   |---|---|---|
   | `python3-colcon-common-extensions` | ❌ 完全没有（main/universe/backports 都没有） | ✅ 0.3.0-100 |
   | `python3-rosdep` | ❌ 只有名字不同的 `python3-rosdep2`（0.21.0-2，旧版） | ✅ 0.27.0-1 |
   | `python3-vcstool` | ❌ 只有 `python3-vcstools`（0.1.42-4） | ✅ 0.3.0-1 |
   | `ros-humble-*`（15 个） | ❌ 命中 0 个 | ✅ 全部命中 |

   实测数据：ROS 2 源 jammy 索引 7858 个包，脚本 18 个依赖全部命中；Ubuntu jammy main+universe 索引 65013 个包，`ros-humble-*` 命中 0 个。

   ⇒ **解法只有一个方向：先把 ROS 2 源配上，再装。** `setup_env.sh` v2 起已加 `[0/6]` 阶段自动完成，实测可达的国内镜像（`InRelease` 均 200，索引大小一致）：

   ```bash
   # 手动等价操作（v2 脚本自动做这四步）
   sudo curl -fsSL https://mirrors.ustc.edu.cn/rosdistro/ros.key -o /usr/share/keyrings/ros-archive-keyring.gpg
   echo 'deb [arch=amd64 signed-by=/usr/share/keyrings/ros-archive-keyring.gpg] https://mirrors.ustc.edu.cn/ros2/ubuntu jammy main' \
     | sudo tee /etc/apt/sources.list.d/ros2.list
   sudo apt update
   ```

   镜像候选（v2 按此顺序探测 fallback）：中科大 → 清华 → 阿里云 → 官方（国内慢，放最后）。
   密钥**只走中科大 rosdistro 镜像**：`raw.githubusercontent.com/ros/rosdistro/master/ros.key` 国内连不上（实测 curl 退出码 35）。官方密钥指纹 `C1CF6E31E6BADE8868B172B4F42ED6FBAB17C654`（Open Robotics <info@osrfoundation.org>，rsa4096，2030-06-01 到期），v2 会校验指纹，防止下到 HTML 错误页还当成功。

   ⚠️ 顺带一提：`gazebo` / `python3-empy` / `python3-catkin-pkg` 在 **universe** 组件里。若实例的 `sources.list` 没开universe，这几个会以同样的「无法定位」报错。v2 会检测并自动启用。

10. **`sudo` 不存在**：魔搭实例常是 root 直登，容器里没装 `sudo`，脚本里每行 `sudo` 都会报 `command not found`。v2 开头做了降级：`[ "$(id -u)" -eq 0 ] && SUDO="" || SUDO="sudo"`。

11. **`colcon build` 报 `_rclpy_pybind11` / `catkin_pkg` 找不到**：魔搭容器默认 `python3` 是 3.11（装在 `/usr/local/bin`），而 ROS Humble 只支持 3.8~3.10。`~/.ros_env` 里的 `export PATH=/usr/bin:$PATH` 能修正大部分情况，但**不校验**——v3 已加显式检查：`/usr/bin/python3` 不是 3.10 就直接停下并说明原因，别等 `colcon build` 报一屏栈。

12. **配好源了、指纹也校验通过，apt 却报 `NO_PUBKEY F42ED6FBAB17C654`（v2 实测翻车）**：
    ```
    由于没有公钥，无法验证下列签名： NO_PUBKEY F42ED6FBAB17C654
    E: 仓库 "https://mirrors.ustc.edu.cn/ros2/ubuntu jammy InRelease" 没有数字签名。
    ```
    ★ **根因：密钥文件权限是 600，`_apt` 用户读不到。**
    apt 验签**不是以 root 跑 gpg**，而是**以 `_apt` 用户身份执行 `gpgv`** 去读那个文件。`_apt` 读不到 600 的文件，等于根本没装 key。

    ★ **为什么自检没抓到（这个坑最值得记）**：`gpg --show-keys` 校验指纹有两个致命漏洞——
    ① 它是**以 root 身份**读的，root 当然能读 600，所以永远显示"校验通过"；
    ② 它只证明"文件里有一把对的公钥"，不证明"**apt 能用上**这把公钥"。

    ★ **还有一个让排查方向彻底跑偏的细节**（同一脚本两条分支行为不一致）：
    | 分支 | 写法 | 产物权限 |
    |---|---|---|
    | 二进制 keyring | `cp "$TMP_KEY" "$KEYRING"` | **600** ← `mktemp` 是 600，`cp` 保留源文件 mode |
    | ASCII armored | `gpg --dearmor > "$KEYRING"` | 644 ← 重定向按 umask 022 创建 |

    两条相邻分支产物权限不同 ⇒ 随机复现，极难定位。v3 已统一 `chmod 644`。

    **解法**（`chmod 644` 是必须的，别漏）：
    ```bash
    sudo chmod 644 /usr/share/keyrings/ros-archive-keyring.gpg
    sudo apt update
    ```

    ⚠️ 顺带记一条通用判据：**给 `signed-by=` 用的 keyring，看权限只看 other 位**（`_apt` 既不是 root 也不是属主，只按 other 权限读）：

    | 权限 | other 位 | `_apt` 能读？ |
    |---|---|---|
    | `600` / `640` / `700` / `400` | 0 | ❌ 必然 NO_PUBKEY |
    | `644` / `604` / `755` | 非 0 | ✅ |

    > 排查小技巧：在 Windows 上开发时测不出这个 bug —— Git Bash 的 `mktemp` 默认给 644，恰好把问题掩盖了。权限类问题必须在 Linux 上验。

13. **一条命令查清密钥问题**：`bash diag_ros_apt_key.sh`（本项目自带）
    用**和 apt 完全相同的视角**（`gpgv --keyring`）逐项查：文件存在 / **权限 other位** / 指纹 / 格式（armored 伪装 `.gpg` 是经典坑）/ `signed-by` 路径一致性 / gpgv 真验签。

    退出码约定：

    | 退出码 | 含义 | 该做什么 |
    |---|---|---|
    | 0 | 全部通过（含gpgv 真验签） | 直接 `apt update` |
    | 2 | 密钥没问题，但**验签这项没跑成**（网络原因） | 跑 `apt update` 看是否还有 NO_PUBKEY |
    | 1 | 检出实质问题 | 按脚本给的命令修 |

14. **★ 检查项"自己没跑成"，却被当成"检查通过"**（v3 实测翻车，比原 bug 更隐蔽）：
    现象是密钥完全正常（权限 644、指纹对、`gpgv` 验签 `Good signature`），但自检那步"拉不到 InRelease"，结果：
    - `setup_env.sh` v3 → 直接 `exit 1` 报「密钥验签没通过」，**白白中断整个安装**；
    - `diag` v1 → 只 `warn` 不计数，最后竟打印「✅ 未发现密钥问题」，**误报**。

    ⇒ 教训：**任何检查项都必须区分「通过 / 失败 / 没验成」三态**。把"没验成"混进"通过"会误报，混进"失败"会误伤。v4 已全面改成三态，网络原因降级放行，交给 `apt update` 出最终结论。

15. **★ bash 陷阱：`cmd | tee log` 的退出码是 `tee` 的，不是 `cmd` 的**（实测确认）：
    ```bash
    if apt update | tee log; then   # ❌ 永远为真，错误处理形同虚设
        echo "成功"                  #    永远走这里
    fi
    ```
    解法二选一：
    ```bash
    set -o pipefail; apt update 2>&1 | tee log; rc=$?; set +o pipefail   # ★ 显式开
    apt update > log 2>&1 || handle_error                              # 不需要看屏幕时更简洁
    ```

    > 这条对 `setup_env.sh` 尤其致命：它用 `set -e`，管道退出码一旦被`tee` 吞掉，
    > 所有错误分支都不会触发，脚本会带着坏状态一路跑到底。

16. **`colcon build` 报 `Could not find a package configuration file provided by "ament_lint_auto"`**（v5 实测踩坑）：
    ```
    CMake Error at CMakeLists.txt:14 (find_package):
    Could not find a package configuration file provided by "ament_lint_auto"
    Failed   <<< navbot_description [3.80s, exited with code 1]
    Aborted  <<< navbot_bringup
    ```
    ★ **不是源码写错了**。`navbot_description` / `navbot_bringup` 的 CMakeLists.txt 里那段是 **`ros2 pkg create` 模板自带的**，连模板刚生成的新包也躲不过：
    ```cmake
    if(BUILD_TESTING)
      find_package(ament_lint_auto REQUIRED)
      ament_lint_auto_find_test_dependencies()
    endif()
    ```
    而 `colcon build` 默认 `BUILD_TESTING=ON` ⇒ 这段会执行 ⇒ **缺包就编译失败**。

    ⇒ 解法（一行）：
    ```bash
    sudo apt install -y ros-humble-ament-lint-auto
    ```
    v5 已把它加进安装清单，并在 `colcon build` 前加依赖预检（缺什么当场补，不等编译报一屏错）。

    > **为什么只装 `ament_lint_auto`、不装 `ament_lint_common`**：
    > · `ament_lint_auto` 自身依赖只有 `ament_cmake-core` / `ament_cmake-test` / `ros-workspace`
    > · `ament_lint_common` 会连带拉进 `copyright` / `cppcheck` / `cpplint` / `flake8` / `pep257` / `uncrustify` / `xmllint` 七八个 linter，而我们不跑 `colcon test`
    > · 缺的 linter 会被 `find_test_dependencies()` 自动跳过，不影响 build
    >
    > ⇒ 够用即可。要跑 `colcon test` 时再补 `ros-humble-ament-lint-common`。

17. **`rosdep init` 在国内必然失败（Errno 104 Connection reset by peer）**（v6 实测踩坑）：
    ```
    ERROR: cannot download default sources list from:
    https://raw.githubusercontent.com/ros/rosdistro/master/rosdep/sources.list.d/20-default.list
    <urlopen error [Errno 104] Connection reset by peer>
    ```
    ★ **根因是"顺序设计错误"，不是网络偶发**：
    `rosdep init` 干的事就是「去下载 `raw.githubusercontent.com` 上的 `20-default.list`」。
    那个域名国内连不上 ⇒ **init 自己就先失败了**，文件根本下载不下来。
    所以「先 init、再把源换成镜像」这个顺序在国内**永远走不到第二步**。

    ⇒ 正确解法：**绕开 init**，直接把 `20-default.list` 写成镜像版内容。
    这份清单只是 rosdep 规则库的**索引**（固定 4 条 yaml URL，不含任何机器相关信息），
    写死是安全的，效果与 init 等价 —— init 的本质就是往这个路径写它。
    ```bash
    sudo mkdir -p /etc/ros/rosdep/sources.list.d
    sudo tee /etc/ros/rosdep/sources.list.d/20-default.list > /dev/null <<'EOF'
    # os-specific listings first
    yaml https://mirrors.tuna.tsinghua.edu.cn/github-raw/ros/rosdistro/master/rosdep/osx-homebrew.yaml osx

    # generic
    yaml https://mirrors.tuna.tsinghua.edu.cn/github-raw/ros/rosdistro/master/rosdep/base.yaml
    yaml https://mirrors.tuna.tsinghua.edu.cn/github-raw/ros/rosdistro/master/rosdep/python.yaml
    yaml https://mirrors.tuna.tsinghua.edu.cn/github-raw/ros/rosdistro/master/rosdep/ruby.yaml
    EOF
    rosdep update
    ```

    ⚠️ **镜像路径别搞混（实测踩过）**：

    | 用途 | 可用地址 | 状态 |
    |---|---|---|
    | rosdep 规则 yaml | `https://mirrors.tuna.tsinghua.edu.cn/github-raw/ros/rosdistro/master/rosdep/*.yaml` | ✅ 200（base 275KB / python 216KB） |
    | ROS 密钥 | `https://mirrors.ustc.edu.cn/rosdistro/ros.key` | ✅ 200 |
    | ~~rosdep 规则 yaml~~ | `https://mirrors.ustc.edu.cn/rosdistro/master/rosdep/*.yaml` | ❌ **404，路径不对** |
    | rosdistro 索引 | `ROSDISTRO_INDEX_URL=...ustc.edu.cn/rosdistro/index-v4.yaml` | ✅（管 `index-v4.yaml`，与上面是两码事） |

    > 💡 **rosdep 失败不影响本项目主线**：`colcon build` 默认模式**不走 rosdep**，
    > 只解析 `package.xml` 的依赖声明；而这些依赖都已用 apt 显式装齐。
    > rosdep 只在你想「按声明自动补装依赖」时才需要。

18. **★ bash 陷阱：`echo"xxx"` 少一个空格，`bash -n` 抓不到**（v6 实测踩坑）：
    ```
    setup_env.sh: 行 495: echo       colcon build 不依赖 rosdep...: 未找到命令
    ```
    `echo"..."` 在 bash 里**语法完全合法** —— 解释器认为你要执行一个名叫
    `echo"       colcon build ..."` 的命令。`bash -n` 会顺利通过，只有**运行时**才炸。

    ⇒ **教训：光靠 `bash -n` 不足以保证脚本正确**。这类错误必须靠实际运行、
    专门扫描（`grep -n 'echo"'`）、或 code review 发现。
    顺带：末段是 `tee`/`sed`/`grep`/`head` 的管道都会吞掉真实退出码，
    凡用管道退出码做判断就必须开 `set -o pipefail`（本脚本现有 4 处，已全配对）。
