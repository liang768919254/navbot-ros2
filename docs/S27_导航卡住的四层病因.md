# S27 复盘：「目标点在墙后面，小车遇到墙就卡在那里了」

> 现象：8 点巡检，PASS 6 / FAIL 2。
> 东南角 `ABORTED`（误差 1.499 m，179 秒），东北角 `SUCCEEDED`（误差 0.256 m，超判据 0.006）。
> 用户原话：**「连续几次了，目标点在墙后面，小车遇到墙就卡在那里了」**
>
> 这篇记的是从「车不动」推到「改哪个数」的完整路径，以及过程中我自己犯的三个错。

---

## 一、先给结论

**「车顶着墙不动」不是一个故障，是四层独立的门槛同时被卡住。**

| 层 | 门槛 | 本项目取值 | 卡在哪 |
|---|---|---|---|
| ① 物理 | 车能塞进缝里：`缝宽 > 2 × robot_radius = 0.400` | — | 缝 E 0.300 → **死路，任何参数都救不回来** |
| ② 能规划 | 缝里有非致命格：`缝宽 > 2 × robot_radius = 0.400` | — | 缝 N 0.450 ✓ 通过 |
| ③ 愿走 | 缝里有**零代价**格：`缝宽 > 2 × inflation_radius` | 0.25 → 要求 0.50 | 缝 N 0.450 → **封死** ← 主犯 |
| ④ 敢停 | 目标点的到达球里有合法车心位置 | `xy_goal_tolerance` 0.15 | 东北角勉强够 ← 次犯 |

修法：
- ③ `inflation_radius` 0.25 → **0.22**
- ④ `xy_goal_tolerance` 0.15 → **0.12**（下面第五节解释为什么反而是收紧）
- 附带 `progress_checker.required_movement_radius` 0.5 → **0.15**
- 附带 `planner_server.GridBased.allow_unknown` true → **false**

**②③ 之间的夹层才是本项目的真正考点。**

```
      0.400        0.450          0.500
        │            │              │
────────┼────────────┼──────────────┼────────
     车宽       缝N 缝宽       2×inflation(0.25)
      ↑            ↑              ↑
   物理能过      落在这个夹层里    零代价门槛
```

落在夹层里意味着：**全局规划器肯画路径，局部控制器不敢执行。**

---

## 二、车为什么是「停住」而不是「乱撞」

看 `live_nav.log` 705~922 行，这是同一条循环重复 17 次、共 179 秒：

```
[bt_navigator]   Begin navigating from (-0.02, 0.05) to (2.20, -1.50)
[controller]     Passing new path to controller.        ← 每秒一条，路径正常
[controller]     Failed to make progress                 ← 10 秒到
[controller]     [follow_path] Aborting handle.
[costmap]        Received request to clear entirely the local_costmap
[controller]     Received a goal, begin computing control effort.   ← 重试
...  重复 17 次 ...
[bt_navigator]   Goal failed
```

关键点是 **`Passing new path to controller` 每秒都在打**。
说明路径一直有、起点没被困、规划器没失败 —— 只是 DWB 从这条路径上找不到可执行的速度。

DWB 的机制：每个周期采样 2000 条候选轨迹（20×5×20），用 critic 打分取最高。
critic 里 `BaseObstacle`(0.02) 和 `PathAlign`(32.0) 会惩罚「踩代价格」和「偏离路径」。
缝 N 整条带代价时：
- 沿路径走 → `BaseObstacle` 罚分
- 离开路径 → `PathAlign` 罚分

两边都罚，最优解就是 **v=0**。DWB 不是撞墙，是**算不出比"不动"更好的选择**。

> ★ 这就是「卡住」和「撞墙」的区别。
> 撞墙会看到车在抖、在蹭；卡住是**车纹丝不动、路径一直有、日志只重复一句 Failed to make progress**。
> 判据：`grep "Passing new path" | wc -l` 远大于 `grep "Reached the goal" | wc -l` ⇒ 卡住不是规划问题。

## 三、`progress_checker` 的 0.5m 是放大器，不是病因

```yaml
required_movement_radius: 0.5   # 10 秒内必须移动 0.5m
movement_time_allowance: 10.0
```

0.5 m / 10 s = 0.05 m/s。而 `max_vel_x` 是 0.22 —— 这个门槛要求车
**在窄缝里匀速不减速地穿过去**，连一次减速微调都不许。

但这条参数**没有造成卡住**，它只造成「卡住之后很吵」：本来卡 3 秒就该触发恢复，
现在要卡 10 秒才触发，17 轮下来浪费了 179 秒。

⇒ 只改这条不改 ③，车照样卡，只是报错更晚。
⇒ 但它必须一起改，否则修好 ③ 之后，车在窄缝里稍微犹豫一下就会被打断。

改成 0.15 m / 10 s（15 mm/s），含义变成「10 秒走不到 15 毫米才是真死」。

---

## 四、`allow_unknown: true` 是第四个病因

```yaml
planner_server.GridBased.allow_unknown: true    # 原值
```

Dijkstra 把未知格当 free 处理。当目标点在隔断另一侧时，
它可能给出「穿过连地图都没建到的区域」的直线路径 —— 正是「目标点在墙后面」
这个描述的来源。

局部 DWB 拿到路径，发现前方 1m 内其实是墙（voxel_layer 用实时激光标成 253），
候选轨迹全撞墙 → v≈0 → 同样表现为卡住。

**为什么改成 false 是安全的**：本项目地图已过 `map_quality.py` 7/7 OK、未知区 0.0%，
不存在「有路但没建出来」。改成 false 就是「只走看得见的路」。

**反过来什么时候要改回 true**：换了建图质量差的地图、发现「明明能走却规划不出来」时。

## 五、第二个 FAIL：东北角 0.256 m —— 容差调紧反而是对的

第一反应是「0.256 只超判据 0.006，把 `TOL_ERR` 放宽到 0.30 就行」。
这个思路错在：**把验收判据削到刚好通过，等于没验收。**

先算清楚：

| 量 | 值 | 说明 |
|---|---|---|
| 东北角到北墙 | 0.550 m | `2.45 - 1.90` |
| 目标点到最近占据格 | 0.354 m | 逐格遍历地图 |
| `xy_goal_tolerance` | 0.15 m | DWB 停进这个球就报 Reached |
| 实测终点误差 | 0.256 m | — |

0.256 > 0.15，说明车在**到达球之外**就停了 —— 不是「停球里偏了点」，
是「球被墙切掉了一块，球外的位置也算到达」。

> ★ 这就是 `xy_goal_tolerance` 的字面陷阱：
> **它沿路径量距离，但车心必须落在代价图的 free 格里。**
> 目标点贴墙时，容差球有一块是非法区，实际可达域比配置值小。

于是出现一个反直觉的结论：**把容差从 0.15 收到 0.12，误差反而变小。**

原因：容差 0.12 意味着 DWB 必须把车开到「离目标 0.12 以内」才允许停，
而 0.12 这个球整个落在合法区里（车心到北墙 0.55，绰绰有余），
于是它只能真的开近 —— 而不是在球边缘随便挑个点停。

为此给 `room_geom.py` 加了 `reachable_center()`：算出「容差球里车心能合法停的最远距离」。
`nav_patrol.py --plan` 现在会打印这一列（可达域），预检阶段就能看出哪个点容易超判据。

## 六、我在这次排查里犯的三个错

**错 1：以为缝 E 能靠降 inflation 救回来。**
缝 E 是 0.300，车宽 0.400 —— 物理 100 mm 差，降 inflation 到 0 也没用。
教训：先算「物理层门槛」`gap vs 2R`，过了这关才轮到调参数。

**错 2：自测断言把「当前值」当成了「期望值」。**
`room_geom.py` 原来断言 `缝N 零代价带 < 0`，写明「规划器会优先绕开」。
改了 inflation 之后自测立刻 FAIL —— 但 FAIL 的不是代码，是断言。
教训：**断言要写恒真性质（`gap - 2·inflation`），不要写死具体数字。**
自测里 PASS 的应该是「关系」，不是「读数」。

**错 3：可达域断言写错过两次，第一次把「最远距离」当「面积」。**
- v1：断言「缝 E 合法域最远 < 0.11」→ 实测 0.150 FAIL。
  缝 E 沿 x 是通的，球在 ±x 方向不受限，最远距离当然到 tol。
- v2：断言「沿 y 跨度 < 0.10」→ 实测 0.270 FAIL。
  忘了缝 E 只是 0.300，跨度天然被 x 方向撑开。
- v3（当前）：取**缝最窄的那一列** `x=1.10` 单独探针 → 跨度 0.000，判定成立。

## 七、排查顺序（下次直接照这个走）

```bash
cd ~/navbot_ws

# ① 参数层面：两处 costmap 是否一致、是否越过 0.6m 通道红线
python3 tools/verify/check_limits.py                     # 应 7 项全 PASS

# ② 几何层面：每条缝过不过得了三层门槛
python3 tools/verify/sim_fullchain/room_geom.py --selftest

# ③ 路线层面：8 个点是否可达、每段最小净空、到点精度上限
python3 tools/verify/sim_fullchain/nav_patrol.py --plan

# ④ 现场：卡住时先看路径有没有在刷新
grep -c "Passing new path to controller" tools/verify/sim_fullchain/live_nav.log
grep -c "Reached the goal"              tools/verify/sim_fullchain/live_nav.log
#   前者 >> 后者  ⇒ 控制器问题（③④层），不是规划问题
#   前者 == 0     ⇒ 规划问题（①②层），看 planner_server 报错

# ⑤ 确认真是 DWB 不敢走、而不是撞了
ros2 topic echo /local_costmap/costmap --once   # 看车前是否一片蓝紫
ros2 topic echo /cmd_vel --once                 # 看 vx 是否恒为 ~0
```

**一句话判据：**

| 现象 | 层 | 先改什么 |
|---|---|---|
| `Goal failed` + 路径一直刷新 + `cmd_vel` 恒 0 | ③ 愿走 | `inflation_radius` 降到「刚好 < 缝宽/2」 |
| `Goal failed` + 无路径 + `Failed to create path` | ①② 规划 | 查 `robot_radius`、`allow_unknown`、目标点净空 |
| `SUCCEEDED` 但误差超判据 | ④ 敢停 | `xy_goal_tolerance` **收紧** + 查目标点是否贴墙 |
| `ABORTED` 很快、报了某条具体 recovery 失败 | 恢复行为 | 查 `behavior_server` / 车是否被围死 |
