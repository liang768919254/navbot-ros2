# S34 —— 避障验证，撞上 AMCL 冻结

> 2026-11-10 夜。本轮目标是「跑通自主避障验证」，实际收获是两个：修好了 `avoid_test.py`
> 自己的两处缺陷，以及发现了一个**优先级更高的定位故障**。

## 一、避障测试本身：设计缺陷已修

### 缺陷 1：目标点和障碍几乎重合，测试无效

第一次跑（旧默认参数 `GOAL=(2.7,-2.0)`）结果看着完美：

```
P1 激光看到障碍    0.130 m  < 0.55   PASS
P2 代价图标成障碍  致命格峰值 706     PASS
P3 车确实绕开      最小 0.351 m > 0.28  PASS
P4 仍到达原目标    SUCCEEDED 误差 0.194 m  PASS
```

但一算几何就发现这局不算数：

| 量 | 值 |
|---|---|
| 目标点到障碍中心 | **0.206 m** |
| 障碍半宽 + 车半宽 | 0.27 m |
| 结论 | **障碍直接压在目标点上** |

障碍插在 `(2.88,-2.10)`，目标点在 `(2.70,-2.00)`。车只要停在误差 0.194 m 处，
P3「绕开 0.351 m」和 P4「到达」就会**同时**看起来通过 —— 其实它压根没绕，
只是停在了障碍旁边。

⇒ 新增 `MIN_GOAL_SEP = 0.70` 前置检查，插障碍前先算距离，
   不够就当场作废并说明原因，不浪费 4 分钟。

⇒ 默认用例换成北走廊横穿：起点 `(2.20,1.90)` → 目标 `(-2.50,1.90)`，
   直线 4.7 m，沿线净空恒为 0.550 m，障碍插在中段，两端都 >2 m。

### 缺陷 2：用 /odom 算判据，坐标系是错的

原来 `Tracker` 只订阅 `/odom`，用它算「距障碍多远」「终点误差多少」。

`/odom` 是里程计坐标系，会漂。实测跑完几轮导航后：

```
AMCL (map 坐标系): (-1.672, 1.241)
odom (里程计坐标系): (-2.918, 1.864)
相差 1.4 m
```

用 odom 坐标去和 map 坐标的目标点比距离，**判据全是错的**。

⇒ 新增 `/amcl_pose` 订阅，轨迹与所有距离判据改用 map 坐标系。
   `/odom` 只保留用于「车有没有起步」这种相对量。

### 缺陷 3（顺带修）：QoS 不兼容，一条消息都收不到

`/amcl_pose` 发布端是 **RELIABLE + TRANSIENT_LOCAL**，
我订阅时写的 `QoSProfile(depth=10)` 默认是 **VOLATILE**。

两者不兼容，订阅端**一条都收不到，且不报错**。现象是
「`ros2 topic echo` 明明有数据，程序里却一直等不到」。
第一次加 `amcl_pose` 订阅时就栽在这儿。

⇒ 显式写 `reliability=RELIABLE, durability=TRANSIENT_LOCAL`。

## 二、撞上的真问题：AMCL 冻结

### 症状

```
$ ros2 run tf2_ros tf2_echo map odom
- Translation: [-1.455, 0.421, 3.372]           ← z = 3.372 m
- Rotation RPY (degree): [-93.5, -70.9, 102.4]  ← 三个轴全乱
```

一个平面差速小车，`map->odom` 只应该有 **x、y 平移和绕 z 一个角度**。
`z=3.372`、`roll=-93°`、`pitch=-71°` 说明 **AMCL 的内部状态跑出了平面**。

配套证据：

| 检查项 | 结果 |
|---|---|
| `/amcl_pose` 时间戳 | 4614 s，而 `/odom` 已到 4944 s —— **落后 330 秒，冻结** |
| `/particle_cloud` | **0 个粒子** |
| Nav2 日志 `Setting pose` | 全部停在 `(16.700000)`，那是启动时注初值的时刻 |
| `Setting pose` 的值 | `-0.000 0.000 -0.000` —— 注入的是原点，`map->odom` 却跑到 z=3.372 |

### 后果

检测循环里车的位置恒定在 `(-2.92, 1.86)` 不动，而 Nav2 那边车其实在跑。
最终 `ABORTED`，`failed to create plan` × 10，`Collision Ahead` × 3。

**不是因为车找不到路，是因为它不知道自己在哪里。**

### 设计缺陷（这才是根）

`live.sh nav` 和 `verify_avoid.sh` 都用 `odom_pose.py` 读 `/odom` 当 AMCL 初值。
`odom_pose.py` 的注释写着：

> 仿真里 map 与 odom 初始重合，AMCL 收敛后两者偏差通常在 0.1m 内

**这个前提只在「刚启动、还没跑过导航」时成立。** 一旦跑过几轮导航，
`map->odom` 会累积偏移（AMCL 用激光校正过），此时拿 odom 坐标当 map 坐标注入，
粒子云就撒在错误位置。

### 已加的防护

`avoid_test.py` 新增 `check_localization()`：
跑测试前先采样 6 次 `/amcl_pose`，若完全不动（<0.1 mm）就当场退出，
并提示去查 `map->odom` 的 z/roll/pitch。

`verify_avoid.sh` 新增「③b 定位健康检查」：
起 Nav2、注初值之后，检查 `map->odom` 的 z 是否在 ±0.05 内，
超了就拒绝继续并提示重启 Nav2。

效果（实测）：从「跑 4 分钟得到错误结论」变成「2 秒内明确告知定位坏了」。

## 三、根治（已完成）

### 方案①　初值不再从 `/odom` 拿 → `set_pose.py` 三种来源

| 模式 | 用法 | 适用 |
|---|---|---|
| `--map x y yaw` | 显式给出 map 坐标 | 冷启动、车确实停在已知点（**最可靠，不依赖任何话题**） |
| `--auto` | 读 `map->odom`，做二维刚体复合 `map_pose = map->odom ∘ odom_pose` 反推 | 车停在任意位置（**默认推荐**） |
| 默认 | 读 `/odom`，保留旧行为但会警告 | 仅供对照 |

`--auto` 的数学依据：`map->odom` 是 `odom` 到 `map` 的刚体变换，
车在 odom 里的位姿经过它复合一次就是 map 位姿。
这样无论 map/odom 漂了多少都能算出正确的 map 坐标。

### 方案②　注入后反查验证 → `verify()` + 自动重试

`set_pose.py` 发完 `/initialpose` 不再直接 `return 0`，而是：

1. 查一次 `map->odom`
2. 判三条：`|z| < 0.02 m`、`|roll| / |pitch| < 2°`
3. 不通过就**重注**，最多 `MAX_TRIES = 3` 次
4. 三次都不通过 → 返回 1，并打印「需要重启 Nav2」的处理步骤

于是「注错了」从**静默**变成**当场可检测**。

### 顺带修掉的一个隐蔽 bug：`verify_avoid.sh` 的 ③b 段

原来用 shell 解析 `ros2 run tf2_ros tf2_echo map odom` 的文本。
`tf2_echo` 每 **1 秒**才打一帧，`head -20` 会抓到 2~3 帧，
提取出的 `TF_Z` 变成多行 `"0.054\n-0.000"`，awk 逐行处理后输出 `"0\n1"`，
字符串比较不成立 —— **判定静默失效，却仍然打印半行 `-0.000` 看着像在工作**。
用户当时报的「z=-0.000 被判成故障」就是这个。

→ 改为调 `loc_check.py`：用 rclpy 直接 `lookup_transform`，拿到的是 float，无解析歧义。

**教训：验证代码本身也会撒谎。** 用文本解析去读结构化数据，再叠加管道截断，
最后得到的是一个「看起来在工作、实际恒为通过」的假检查。

## 教训

1. **判据必须和坐标系对齐。** 「用 odom 坐标算和 map 坐标目标的距离」这种错，
   代码看起来很自然，结果静默错误。
2. **QoS 不兼容不报错。** RELIABLE/TRANSIENT_LOCAL 的发布端配 VOLATILE 订阅端，
   收不到就是收不到，没有任何提示。
3. **测试用例的几何要先算再跑。** 障碍压在目标点上时，P3 和 P4 会同时假通过。
4. **`live.sh nav` 的初值注入有隐含前提。** 「odom 与 map 重合」只在冷启动成立，
   跑过导航后就不成立，必须重新设计。
5. **验证脚本要能拒绝执行。** 定位坏了还硬跑，产出的是一堆有结论的错数据，
   比不跑更糟。
6. **「消息发出去了」≠「目标达成了」。** `set_pose.py` 发完 `/initialpose` 就
   `return 0`，上游据此认为成功 —— 中间隔着一整个 AMCL 收敛过程，没人检查。
   凡是「发请求 / 下命令」的脚本，都要有关键状态的**反向确认**。
7. **别拿旧输出当新证据。** 改完代码后仍在追 `x744`，其实那是改之前那版的日志；
   新版实测 `x39`（3 s @10 Hz）。改完之后**先重跑一次再判断**。

# 六、避障验证首次全 PASS（S36，2026-11-10 深夜）

## 结果

```
目标 (2.30, 1.70)，东侧竖通道，净空 0.650，扣除膨胀后可通行带 +0.180 m

P1 激光看到障碍      最近 0.166 m  < 0.55      PASS
P2 代价图标成障碍    致命格峰值 911/2933        PASS
P3 车确实绕开        与障碍最小 0.371 m > 0.30  PASS
P4 仍到达原目标      SUCCEEDED  误差 0.121 m    PASS

导航 SUCCEEDED，31.2 s
```

## 途中修掉的两个判据 bug（都是自己写的）

### ① `check_localization()` 判据与调用时机矛盾

第一版判据：「采样 `/amcl_pose`，位姿必须有变化」。
但调用点在**车还没起步**的时候 —— 车静止，位姿本来就不该变。

更深的层：`nav2_params.yaml` 里

```yaml
update_min_d: 0.10    # 移动超过 10 cm 才做一次更新
update_min_a: 0.10    # 转动超过 6° 才做一次更新
```

**AMCL 是事件驱动的**，车不动时它根本不发新的 `/amcl_pose`。
所以「不动」在这套配置下是**正常行为**，拿它当冻结判据，
等于要求一辆停着的车跑出里程。

→ 改成检查 `map->odom` 的 z / roll / pitch 与平移漂移。
这些都是**静态可测**的，不需要车动，而且 `map->odom` 跑出平面
正是 AMCL 坏掉的直接证据（S34 那次是 z=3.372、roll=-93°）。

### ② P3 的 `mind` 取了全轨迹 —— 结构性永不可能通过

```python
mind = min(math.hypot(x - ox, y - oy) for _, x, y in node.trace)  # 旧
```

障碍是按「车前方 1.2 m」算出来的，也就是 **插在车已经走过的路线上**。
插入前车必然路过那个位置，所以 `mind` 恒约等于 0。

实测报「与障碍最小 0.028 m」，而 Gazebo 里根本没碰撞 —— 那 0.028
就是插入前车压过该点留下的痕迹。

→ 记录 `t_insert`，P3 只统计 `t >= t_insert` 的轨迹点。

## ★ 最重要的认知：场地要用「可通行带」算，不能凭感觉选

```
可通行带 = (车心净空 - inflation) - (障碍半宽 + inflation)
```

以 `inflation = 0.16`、障碍半宽 `0.15` 计：

| 场地 | 净空 | 可通行带 | 实测结果 |
|---|---|---|---|
| 南走廊 | 0.450 | **−0.020** | 数学上不可行 |
| 北走廊 | 0.550 | **+0.080** | 卡死 60 s，`failed to create plan` ×2 |
| 东侧 x=2.30 | 0.650 | **+0.180** | 一次 PASS |

北走廊那次差点得出「避障能力不行」的结论。实际是**用例把可行空间
压到 8 cm** —— 规划器在 8 cm 宽的带里找连续路径，找不到是正常的，
不是算法缺陷。

→ 已在 `avoid_test.py` 加前置闸门：可通行带 < 0.10 m 直接作废（返回码 6），
不再浪费 4 分钟跑完才发现。

## `P3_CLEAR` 从 0.28 改 0.30

| 概念 | 数值 | 含义 |
|---|---|---|
| 物理贴脸 | 0.12 + 0.15 = **0.27** | 车边贴到箱边 |
| 膨胀禁区 | 0.15 + 0.16 = **0.31** | 局部代价图的致命格边界 |
| 旧判据 | 0.28 | 两边不靠：既容许物理贴脸，又低于膨胀禁区 |
| 新判据 | **0.30** | 「贴在膨胀边界上擦过」的合理下限 |

## `verify_avoid.sh` 收尾策略也改了

- 又一处 `timeout python3 avoid_test.py | grep` 吞返回码（本文件第三次），
  改成 `VAR=$(...) ; RC=$?`。
- **失败时保留 Gazebo / Nav2 / RViz**，不再一律 stop。
  原来失败后想复查看现场，还得重启 Nav2 再重注初值 ——
  而重注初值正是上一轮踩循环依赖的地方，没必要每次都赌。

## 新增教训

8. **判据要和「被测对象的实际行为」对齐。** AMCL 是事件驱动、车不动就不发消息，
   拿「消息有没有变」当健康判据，测的是车动没动，不是定位好不好。
9. **判据的统计范围要和方法论一致。** 「车有没有绕开障碍」必须只统计障碍出现后的轨迹，
   把插入前压过该点的历史算进去，等于永远算出 0。
10. **测试用例的可行空间要先算再跑。** 差 0.1 m 的净空，结论从「算法不行」变成「算法没问题」。
    `room_geom.py` 已经能算净空，拿来算可通行带是顺手的事。
