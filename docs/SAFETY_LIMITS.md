# safety_limits —— navbot 安全阈值的唯一来源

> 借鉴自 `ros2-gazebo-robot-lab` 的 `safety_contract.py` 思路：
> **阈值只定义一次，规划器与急停共用，且写下推导过程。**
>
> ★ 本文是「为什么是这些数」的权威说明。
>   `nav2_params.yaml` 里只写数值，并在注释里注明「来源：safety_limits.md」。
>   改阈值必须同步改这里，否则 `tools/verify/check_limits.py` 会报出来。

---

## 一、车身几何（一切的起点）

| 量 | 值 | 依据 |
|---|---|---|
| 车体宽度 | 0.20 m | URDF `base_link` 的 box 尺寸 |
| 车体长度 | 0.20 m | 同上 |
| 等效外接半径 | **0.20 m** | 对角线的 1/2 ≈ 0.141，加上轮子外伸，取 0.20 保守值 |
| 轮距 | 0.16 m | `left_wheel_link` 与 `right_wheel_link` 的 y 间距 |
| 轮半径 | 0.0325 m | URDF cylinder radius |
| 雷达安装高 | 0.18 m | `laser_link` 相对 `base_footprint` 的 z |
| 雷达相对车心 | (0, 0) | 与车心重合，**无偏置**（参考项目有 -0.7057 m 的偏置，因为它把雷达装在车头） |

**为什么"无偏置"值得记一笔**：参考项目必须在线查 `base_link → lidar` TF 再算扫掠。
你没有偏置，路径检查可以简化——但**这个简化依赖上面这行假设**，车型一改就得重做。

## 二、场景约束（决定了 inflation 的上限）

| 量 | 值 | 依据 |
|---|---|---|
| 房间尺寸 | 6.0 × 5.0 m | `navbot_room.world` 四面墙 |
| **最窄通道全宽** | **0.60 m** | 墙与隔断之间的可通行净宽 |
| **真正的瓶颈：缝 N** | **0.450 m** | `partition_mid` 下沿 y=0.455 ↔ `partition_short` 北端 y=0.005（★ 2026-11-10 补：这才是封死车的那条缝，不是 0.6 m 那条） |
| 通道半宽 | 0.30 m | 0.60 / 2 |

## 三、代价地图膨胀（由上面两节推导）

```
约束：2 × inflation_radius < 通道全宽
     2 × inflation_radius < 0.60
     ⇒ inflation_radius < 0.30

取值：inflation_radius = 0.16      （2026-11-10 夜从 0.22 改，见下）
     cost_scaling_factor = 5.0     （配合上式，见下）
     车体模型             = footprint 矩形 0.30×0.24（不再是 robot_radius 0.20）
```

**★★ 2026-11-10 夜（S32）：0.22 → 0.16。这次改的是「车体模型」，不是膨胀本身。**

上面整段推导的前提是「车被当成半径 0.20 的圆」。这个前提本身是错的：

```
外接圆半径       = sqrt(0.15² + 0.12²) = 0.192   ← 圆模型用的
车宽一半（贴边） = 0.12                          ← 矩形贴边实际占的
         差距   = 0.072 m                      ← 凭空胖了 7.2 cm
```

在一条 0.655 m 的缝里，多算 7.2 cm × 2 侧 = **14.4 cm 的假障碍**。
缝 S 的车心合法带因此从 0.415 m 缩到 0.255 m，而车实际只需要 0.24 m 总宽 ——
**物理能过，代价图判死**。这就是「从上面能过去、从下面一直卡住」的根因。

改成矩形足迹后，`inscribed_radius = min(0.30, 0.24)/2 = 0.12`，
膨胀半径只要覆盖它 + 缓冲：

```
取值：inflation_radius = 0.12 + 0.04 = 0.16
```

| 通道 | 缝宽 | 圆 0.20 / infl 0.22（旧） | 矩形 0.30×0.24 / infl 0.16（新） |
|---|---|---|---|
| 缝E | 0.300 | 物理死路 | 物理死路（0.300 > 2×0.12=0.24，**其实能过了**） |
| 缝N | 0.450 | 零代价带 −0.050 | 零代价带 **+0.130** |
| 缝S | 0.655 | 零代价带 0.215 | 零代价带 **0.335** |
| 缝W | 1.167 | 0.726 | 0.846 |

> ★ 注意缝 E：0.300 > 0.24，矩形模型下它**从死路变成了能走的缝**（余量 6 cm）。
> 但代价图给它留的零代价带是 `0.300 − 0.32 = −0.02`，仍然是负的 ——
> 所以实际还是不走。**这提醒一件事：物理能过 ≠ 零代价能过，两本账要分开记。**

**★ 换模型必须同时降膨胀，否则白换。**
只把 `robot_radius` 换成 `footprint` 而保留 `inflation_radius: 0.22`，
膨胀层照样按 0.22 往外推，缝 S 的账一点不变 ——
而且这时候 YAML 看着「已经改对了」，比不改更难查。
两处 costmap 的 `inflation_radius` 必须一起改。

**★ 必须承认的副作用：膨胀衰减区没了。**
`0.16 < 圆半径 0.20`，而 `d < radius → 253`、`d ≥ inflation → 0`，
两者之间没有区间 ⇒ 代价图从「253 → 缓坡 → 0」变成「253 → 0」的硬台阶。
缓解靠 `BaseObstacle.scale: 0.5`（让 DWB 主动远离 253 边界）。
真机上若发现车角蹭墙，优先把 `footprint` 从 4 顶点加到 8 顶点（边中点），
而不是把 `inflation_radius` 加回去。

**为什么当初 0.25 和 0.22 都不对：** 它们解决的是「缝 N 太窄」，
但缝 N 只是症状；真正的病是「车被算胖了」。胖着看病，只能不断压缩膨胀，
越压越不安全，最终还是判死缝 S。**换模型是把病因去掉，压膨胀只是打补丁。**

**为什么 `cost_scaling_factor = 5.0` 保留：**
这个参数只影响 253 与 0 之间的过渡形状。现在 `inflation 0.16 < radius 0.20`，
过渡区被吃掉了，5.0 在当前配置下**不产生可见效果**（它仍然正确，
哪天把 inflation 调回 > 0.20 就立刻生效）。保留 5.0 是为了让
「调回圆模型」这条退路随时可用。

| 位置 | 参数 | 值 |
|---|---|---|
| `nav2_params.yaml` global_costmap | `footprint` | `[[0.15,0.12],[0.15,-0.12],[-0.15,-0.12],[-0.15,0.12]]` |
| `nav2_params.yaml` global_costmap | `inflation_radius` | 0.16 |
| `nav2_params.yaml` global_costmap | `cost_scaling_factor` | 5.0 |
| `nav2_params.yaml` local_costmap | `footprint` | 同上（必须一致） |
| `nav2_params.yaml` local_costmap | `inflation_radius` | 0.16 |
| `nav2_params.yaml` local_costmap | `cost_scaling_factor` | 5.0 |

**`footprint` 与 `robot_radius` 在 Nav2 里互斥**：
只要写了 `footprint`，`robot_radius` 就被静默忽略。
所以这次把 `robot_radius` 整行删掉，而不是注释掉 —— 留着只会误导后来人。

改完这几处（参数 + 本文件 + `tools/verify/check_limits.py` 的 `EXPECTED_INFLATION`）
跑一遍一致性检查：

```bash
python3 tools/verify/check_limits.py     # 应 10 项全 PASS（含 ②b 车体模型节）
python3 tools/verify/check_controller.py # 应 12 项全 PASS
python3 tools/verify/inject_faults.py    # 应 9/9 全抓到
python3 tools/verify/sim_fullchain/room_geom.py --selftest   # 应全 PASS
```

### 三补：上一轮「0.25 → 0.22」的修正记录（已过时，留作对照）

> 这一段记录的是 **圆模型时代** 的推导。S32 换矩形足迹后，结论已被上面的
> 「0.22 → 0.16」取代。**保留它是因为它记录了一个思维陷阱：**
> 当时我把「缝 N 太窄」当成病因，不断压缩膨胀半径去打补丁，
> 越压越不安全，而真正的病是「车被算胖了 7.2 cm」。
> **压参数治标，换模型治本。**

当时的事实链（仍然成立，只是前提变了）：

| 通道 | 缝宽 | `2×0.25=0.50` 时 | `2×0.22=0.44` 时 |
|---|---|---|---|
| 缝E | 0.300 | 物理就比车窄（0.40），死路 | 同左，救不回来 |
| 缝N | **0.450** | **零代价带 −0.050 → 整条缝带代价** | **零代价带 +0.010 → 能走** |
| 缝S | 0.655 | 零代价带 0.155 | 0.215 |
| 缝W | 1.167 | 零代价带 0.666 | 0.726 |

关键区分是「能规划」≠「能走」：
- **能规划**的条件是 `缝宽 > 2 × inscribed_radius`
- **能走**（DWB 敢执行）的条件是 `缝宽 > 2 × inflation_radius`

缝 N 落在 0.44 和 0.50 之间（圆模型下注册半径 0.20 → 2×0.20=0.40）。
于是全局 Navfn 因为绕行更贵、仍把路径画过缝 N，
而局部 DWB 每条候选轨迹都踩代价格，打不出可接受的分 → 输出 v≈0
→ `progress_checker` 判卡住 → 恢复行为转圈/后退 → 重规划回同一条路 → 死循环。

**这段推导的三个结论现在仍然有效：**
1. 「能规划」和「能走」是两本账，门槛不同；
2. 取 0.29 这类贴近上限的值会因跟随误差（实测终点误差 0.092~0.134 m）频繁报
   「起点不在自由空间」；
3. `cost_scaling_factor` 只影响 253 与 0 之间的过渡形状，不能代替膨胀半径。

**唯一被推翻的结论：** 「0.22 是最小安全值，不要再往下压」。
—— 那句话的前提是「车半径 0.20」。换成矩形足迹后，注册半径降到 0.12，
0.16 反而比 0.22 更贴合实际车体。

## 四、避障验收判据（由几何推导）

动态避障测试插入 0.35 × 0.35 m 的箱子，半宽 0.175 m。

```
车心到障碍边缘的理论最小距离（刚好擦过）
  = 车外接半径 + 障碍半宽
  = 0.20 + 0.175
  = 0.375 m

若要"明显绕开"，应在理论值上留余量
  ⇒ 判据：车心到障碍边缘 > 0.30 m  （比理论擦过距离小，但比膨胀半径大）
```

⚠️ **这里有个已知的宽松之处**：`avoid_test.py` 用的是"车心到障碍边缘 > 0.28 m"
（`mind > 0.28`），比上面的 0.30 更松。原因是"边缘距离"和"车心距离"口径不同，
且实测值 0.495 m 远大于两者。**记录在此，避免以后误以为判据是 0.30。**

| 判据 | 阈值 | 位置 |
|---|---|---|
| 激光看到障碍 | < 0.40 m 有一簇点 | `avoid_test.py` |
| 代价图标记 | 致命格数 > 50 | `avoid_test.py` |
| 与障碍最小距离 | > 0.28 m | `avoid_test.py:181` |
| 仍到达目标 | 终点误差 < 0.30 m | `avoid_test.py:182` |

## 五、急停 / guard 阈值（当前**未实现**，预留）

参考项目有一套独立的 `velocity_guard`：指令超时 0.5 s、扫描超时 1.5 s、
障碍进入 1.9 m 停车。你现在完全靠 Nav2 的 costmap + DWB 自身的碰撞检查。

**若以后要加真机 guard，建议值**（未验证，仅推导）：

| 量 | 建议值 | 推导 |
|---|---|---|
| 指令超时 | 0.5 s | 遥控断连后应在半秒内停 |
| 扫描超时 | 1.5 s | 10Hz 雷达丢 15 帧 = 通信已异常 |
| 停车距离 | 0.35 m | 车半径 0.20 + 单周期滑行 ~0.11（0.22 m/s × 0.05 s）+ 余量 |

⚠️ **必须用 `STEADY_TIME` 时钟计超时，不能用仿真时钟**：
`use_sim_time:=true` 时若 Gazebo RTF 掉到 1/3，用仿真时钟的 guard 会从 20Hz 变 6.7Hz，
急停响应慢 3 倍——这是真实隐患，不是理论问题。
