# H3 · 室内建图 / 定位 / 避障 落地路线

> 2026-10-31。小车卡了几天，这份文档回答一个问题：**从今天的现状出发，最短路径是什么。**

## 一、现状盘点（不粉饰）

| 层 | 状态 | 卡点 |
|---|---|---|
| 机械 | ✅ 装配完成 | — |
| STM32 固件 | ⚠️ 只有 **R5 雷达扫描固件** | **没有底盘控制固件**，`firmware/navbot_chassis` 是 CubeMX 骨架，19 个 TODO 空着 |
| 雷达 | ❌ `rx=0`，一个字节都没收到 | 接在 MCU 的 USART3（PB10/PB11），线路无电平变化 |
| ESP8266 | ❌ 不可访问 | 焊在 PCB 上，接 STM32 的 USART2，固件没做 AT 透传 |
| PC 软件 | ✅ 仿真跑通，`navbot_bridge` 36 项测试通过 | **真机从未接上过** |

### 一句话诊断

建图/定位/避障需要的输入是 `/scan` + `/odom` + TF。
**现在这两路数据一个都没有**——一个被卡在雷达硬件，一个被卡在固件没写。
所以不是「算法没调好」，是**输入端是空的**。

## 二、最重要的一个决策：雷达改接 PC

### 现在的接法

```
RPLIDAR ──UART──> STM32 (USART3) ──CH340──> PC
                   ↑ 要同时跑：电机 PID + 雷达解析 + 扇区统计 + 串口上报
```

F103C8T6 只有 72 MHz / 20 KB RAM。R5 固件的扇区表已经占了 864 B，
再叠上电机闭环和 PID，实时性风险很高。而且雷达现在 `rx=0`，两天没修通。

### 建议改成的接法

```
RPLIDAR ──USB 转接板(CP210x)──> 上位机：rplidar_ros  →  /scan
STM32   ──CH340──> 上位机：navbot_bridge → /odom
```

| | 收益 | 代价 |
|---|---|---|
| 雷达 | `rplidar_ros` 2.1.4 现成（`~/ros2_ws` 里已有），全分辨率（≈0.9°/点） | 多一根 USB 线 |
| MCU | 只专注电机 + 编码器，实时性有保障 | 失去 R5 的舵机联动三维扫描 |
| 诊断 | 雷达接上位机一插就知道好坏，**绕开 `rx=0` 这个死结** | — |

**关键点：`rx=0` 不需要「修好」，只需要「不再需要它」。**
舵机三维扫描是加分项，不是建图的前提。先把主流程跑通，回头再谈它。

> 如果你坚持雷达留在 MCU 上，那必须先解决 `rx=0`（量 PB11 和雷达 TX 是否导通），
> 再写一个 `scan_bridge` 解析 `S,idx,world_deg,min,avg,max,cnt` 转 LaserScan。
> 这条路多 2~3 天的活，而且分辨率掉到 5°。

## 三、车要自己跑：主控必须上车

上面只解决了**数据从哪来**，没解决**计算放在哪**。这两件事必须分开谈。

### 硬约束

自主导航时车要自己走遍房间、自己绕开椅子，**没有人跟着它**。
所以跑 ROS 2 的那台机器必须**装在车上**，由车上电池供电，通过 WiFi 和你的笔记本通信。

```
笔记本放在桌上拖着 USB 线 → 那叫「有线遥控测试」，不叫自主导航
```

这就是原 PCB 上焊 ESP8266 的本意：让车能脱线。但 ESP8266 只有 80 KB RAM，
跑不了 ROS 2，只能做串口→TCP 透传；而雷达数据若要走
`雷达→STM32→ESP8266→WiFi→笔记本`，带宽和延迟都撑不住实时建图。**这条路不通。**

### 怎么办：分两个阶段，不必一次买齐

| 阶段 | 计算放在哪 | 能不能脱线 | 用途 |
|---|---|---|---|
| **建图（阶段 2）** | 笔记本放桌上 + 长 USB 线（3~5 m） | ❌ 拖着线 | **够用**。人推车走一圈，线跟着走，房间不大的话完全可行 |
| **自主导航（阶段 3）** | 必须装车上 | ✅ | 这时才需要车载主控 |

**关键：建图和自主导航对「计算在哪」的要求不同。**
建图是人推着走，线不是问题；自主导航才必须脱线。

所以路线不是「先买车载主控再开工」，而是：

1. 阶段 0~2 全用桌面上那台笔记本 + 长 USB 线，**今天就能开始**
2. 阶段 3 前半段（3a）也先用线缆验证算法——车拖着线跑 Nav2，
   验证「路径规划对不对、会不会绕开椅子」
3. 算法验证通过后再上车载主控（阶段 3b），
   **软件一行不改**，只是把同一套 ROS 2 从桌上搬到车上

> 这样能在一周内看到「车自己绕开椅子到达目标点」，只是线还连着。
> 比起等硬件到货再开工，心理上和技术上都更稳。

### 车载主控选型（阶段 3b 才需要）

| 方案 | 价格 | 供电 | 软件 | 评价 |
|---|---|---|---|---|
| **树莓派 4B 4G/8G** | 500~700 | 5V 3A，可直接吃车上现成的 5V 降压 | arm64，Humble 官方支持 | **最省心**，功耗 3~6 W，车架扛得住 |
| **N100 迷你主机** | 700~900 | 12V，需要额外 DC-DC | x86，和你现在的开发机完全一致 | 性能强得多，编译调试零学习成本；但要解决 12V 供电和重量 |
| Jetson Nano 二手 | 800~1000 | 5V 4A | Ubuntu 18.04 底子，Humble 要折腾 | 不推荐，除非以后要跑视觉 |

**建议树莓派 4B**：供电最简单（车上已有 5V 降压给 STM32 和雷达），
功耗低，ROS 2 支持成熟。以后要加视觉再考虑 x86 或 Orin Nano。

> 等树莓派到货的这几天不要空等——阶段 0~2 用笔记本照常推进。

## 四、六个关卡

### 阶段 0 · 雷达出数据（今晚，约 15 分钟）

雷达用 USB 转接板接电脑：

```bash
source /opt/ros/humble/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 launch rplidar_ros rplidar_a1_launch.py serial_port:=/dev/ttyUSB1
```

**验收判据**

| # | 判据 | 命令 | 期望 |
|---|---|---|---|
| 1 | 设备枚举 | `lsusb \| grep 10c4` | 看到 `CP210x` |
| 2 | 话题有频率 | `ros2 topic hz /scan` | 8~12 Hz |
| 3 | RViz 有点 | 加 LaserScan，topic `/scan` | 看到房间轮廓 |
| 4 | 量程合理 | 看 RViz 里最远点 | 几米内，不是全 0 或全 inf |

**如果判据 2 不过**：雷达本身有问题，先换转接板/换线，别急着往下走。

> 这一步同时完成了「验雷达」和「出 /scan」两件事。**今晚就能看到点云。**

### 阶段 1a · 车能遥控走 + 有 /odom（约半天）

写固件，只做三件事：

```
V 帧到达 → 解析 vel_l / vel_r → 换算 PWM → 驱动电机
编码器中断 → 累加计数 → 50 Hz 编 O 帧 → 串口发出
600 ms 没收到 V 帧 → PWM 归零（丢帧保护）
```

**这一阶段不做速度闭环 PID。** 开环就能遥控走，`/odom` 精度够建图用。
把 PID 推到 1b，先让车动起来拿到正反馈。

**验收判据**

| # | 判据 | 期望 |
|---|---|---|
| 1 | 遥控能走 | 按方向键，两轮都转，方向正确 |
| 2 | `/odom` 频率 | 45~55 Hz |
| 3 | 帧不丢 | `seq` 连续，无跳变 |
| 4 | 直行 1 m | 卷尺量实际位移，与 odom 累计误差 < 5% |
| 5 | 原地转 360° | RViz 里轨迹闭合，首尾角度差 < 10° |
| 6 | **拔串口** | 600 ms 内停车（这条最重要，别让车撞墙） |

### 阶段 1b · 速度闭环（约半天）

加 PID：目标速度 vs 编码器实测速度 → PWM 修正。

**验收判据**

| # | 判据 | 期望 |
|---|---|---|
| 1 | 阶跃响应 | 给定 0.2 m/s，200 ms 内到 90%，无持续振荡 |
| 2 | 稳态误差 | 稳定后 < 5% |
| 3 | 两轮一致 | 直线走 2 m，横向偏移 < 5 cm |

> 阶段 2 建图用 1a 就够，1b 是给 Nav2 准备的（Nav2 依赖较准的速度执行）。

### 阶段 2 · 建图（约半天）

```bash
# 终端 1：雷达
ros2 launch rplidar_ros rplidar_a1_launch.py
# 终端 2：底盘桥
ros2 run navbot_bridge chassis_bridge --ros-args -p port:=/dev/ttyUSB0
# 终端 3：建图
ros2 launch navbot_bringup slam_mapping.launch.py use_sim_time:=false
# 终端 4：遥控
ros2 run teleop_twist_keyboard teleop_twist_keyboard
```

**验收判据**

| # | 判据 | 期望 |
|---|---|---|
| 1 | `/map` 有帧 | `ros2 topic hz /map` ≈ 0.2 Hz |
| 2 | 墙是直的 | RViz 里墙面无锯齿、无重影 |
| 3 | 闭环 | 走一圈回到起点，起始位置墙面重合 |
| 4 | 尺寸准 | 地图上量房间长宽，与实测误差 < 10% |

存图：`ros2 run nav2_map_server map_saver_cli -f navbot_room`

### 阶段 3a · 定位 + 避障（有线验证算法，约半天）

**车还拖着 USB 线，笔记本还在桌上。** 目的不是「完全自主」，而是验证
「Nav2 能不能规划出正确路径、会不会绕开障碍」——算法对了，硬件形态随时能换。

```bash
ros2 launch navbot_bringup nav_bringup.launch.py use_sim_time:=false
```

RViz 里点 **2D Pose Estimate** 给初始位姿，再点 **Nav2 Goal**。

**验收判据**

| # | 判据 | 期望 |
|---|---|---|
| 1 | 定位收敛 | 给初始位姿后，粒子云收敛到车周围 |
| 2 | 单点到达 | 直线上 2 m 外的点，能到，终点误差 < 15 cm |
| 3 | **连续 5 点** | 依次给 5 个点，5/5 到达（这是 README 里记的 G1 空洞） |
| 4 | **静态避障** | 路径上放个椅子，车能绕开或重规划 |
| 5 | 不撞墙 | 全程在代价地图边界内，无碰撞 |

> 这一步有根线确实别扭，但**判据全都能验**。线只在车走远时会拽住，
> 把 5 个点都放在 2 m 半径内就行。

### 阶段 3b · 装车载主控，真正脱线（约半天）

树莓派到货后：

1. 烧 Ubuntu 22.04 Server arm64 + 装 ROS 2 Humble
2. 把 `navbot_ws` 整个 rsync 过去，`colcon build`（x86 上编译过的包，arm64 大多直接能编）
3. 雷达、STM32 都插树莓派，5V 从车上降压模块取
4. 树莓派连家里 WiFi，笔记本设同一个 `ROS_DOMAIN_ID`
5. 车上电 → 笔记本 `ros2 topic list` 能看到 `/scan` `/odom`，RViz 远程可视化

**验收判据**

| # | 判据 | 期望 |
|---|---|---|
| 1 | 跨机可见 | 笔记本上 `ros2 topic hz /scan` 有频率（走 WiFi） |
| 2 | 延迟可接受 | `/scan` 端到端延迟 < 100 ms（`ros2 topic delay`） |
| 3 | 重复阶段 3a | 同样 5 个点，去掉线缆，5/5 到达 |
| 4 | 续航 | 电池满电跑完一轮 5 点不中断 |

> **软件一行不改**——同一套 ROS 2 从桌上搬到车上。这正是当初选 ROS 2 的意义。
> 唯一要改的是 `ROS_DOMAIN_ID` 和可能的 `RMW_IMPLEMENTATION`（跨机时 fastrtps 要开 UDP，
> 参考 `tools/diag/fastdds_udp_only.xml`）。

## 五、明确不做的四件事

| 不做 | 原因 |
|---|---|
| **ESP8266 AT 透传** | 它只有 80 KB RAM，跑不了 ROS 2，只能做串口→TCP 透传。雷达数据若走 `STM32→ESP→WiFi→笔记本`，带宽和延迟都撑不住实时建图。**脱线的正解是车载主控（阶段 3b），不是 ESP** |
| C++ 版 `navbot_chassis` | Python 版 `navbot_bridge` 已过 36 项测试，性能足够（50 Hz 文本帧）。C++ 版是练手，不是需求 |
| 舵机三维扫描 | R5 固件的活。单线雷达二维建图已经够室内避障 |
| 摄像头视觉 | 超出当前目标 |

> ESP8266 唯一还值得做的用法：**设备状态上报**（电量、温度、在线状态），
> 走轻量 MQTT，不碰雷达数据。那是阶段 3b 之后的事。

## 六、每个阶段卡住了怎么办

| 阶段 | 卡超过 | 降级方案 |
|---|---|---|
| 0 | 2 小时 | 雷达换一根 USB 线、换转接板；仍不出点就是雷达坏，先借一个/返修 |
| 1a | 1 天 | 先只做「V 帧 → PWM」，`/odom` 用 `tools/verify/fake_chassis.py` 顶着，把阶段 2 先跑通 |
| 1b | 1 天 | 跳过，用 1a 的开环去跑 Nav2，把 `max_vel` 降到 0.15 m/s 补偿精度 |
| 2 | 1 天 | 用仿真地图先验证 Nav2 参数（`nav_bringup.launch.py use_sim_time:=true`），真机只做最后一步 |
| 3a | 2 天 | 只验「单点到达 + 静态避障」，动态避障留到 3b 之后 |
| 3b | 树莓派没到 | **笔记本驮车上**（2 kg，用电池，低速短距离），拍一段脱线演示；等硬件到了再换 |

**降级的目的是保证主流程能推进，不是放弃。**
