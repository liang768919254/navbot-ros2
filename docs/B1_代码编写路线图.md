**让一台两轮差速小车，在仿真里能建图、能导航；把同一套模型接到真实 STM32 底盘上，用 Nav2 驱动它走。**

### D2 节点数量：一个 `chassis_bridge` 还是拆两个？

**推荐：单节点 `chassis_bridge`**，内部用两个类（`SerialReader` / `OdomPublisher`）分层。

- 理由：串口是**独占资源**，拆两节点要么各开一次串口（冲突），
  要么跨进程共享句柄（复杂且易崩）。单进程内用「串口读线程 + ROS 定时器」最稳。

### D3 串口读取的并发模型？

**候选 A**：`serial` 设 `timeout=0.005`，在 ROS 定时器里非阻塞读 + 累积缓冲区。
**候选 B**：独立读线程 + 队列，ROS 定时器只从队列取。

**推荐 A**。理由：
- 20ms 周期下，5ms 超时的阻塞在最坏情况只吃掉 25% 周期，可接受
- 无跨线程共享状态，无锁，代码量少一半
- 缓冲处理仍要按 `\n` 切分并保留残缺尾巴（**这是唯一的真正难点**）

> ★ `fake_chassis.py:188-189` 留了提示：「`timeout` 不能设 `None`（阻塞），否则 `readline` 会永久占住循环」。
> 这句话是对的，但它的结论是「必须另开线程」——我给的是更轻的替代方案。
> 若实测 50Hz 掉帧（`ros2 topic hz /odom` 低于 45），再升级到候选 B。

### D4 里程计的速度来源：`vel_l/vel_r` 还是编码器增量？

**推荐：以编码器增量为主，`vel_*` 仅用于填 `twist`。**

| 方案 | 问题 |
|---|---|
| 只用 `vel_*` | MCU 已做一次换算，PC 再做一次；`--zero-drift` 注入下无法察觉零点偏移 |
| 只用编码器 | 静止抖动直接进位姿积分，`/odom` 缓慢漂移 |
| **编码器 + 死区 → 位姿；`vel_*` → twist** | 推荐 |

**必须实现死区**：`|Δenc| ≤ 2` 脉冲时置零。
理由（`test_protocol.py:277` 已算出）：2 个脉冲抖动 = 9.67 mm/s，
不做死区则静止时 `/odom` 会以 9.67mm/s 持续「爬行」。

### D7 `tick_ms` 时间戳校正做不做？

协议 §二【3】要求用 MCU 时间戳做采样时刻校正。

**决策：做，但只做「一次性偏移估计」，不做时钟同步。**

- 收到第一帧时记录 `offset = pc_time - tick_ms`，之后 `header.stamp = now - (0.02/2)`（半个周期）
- 理由：PC 与 MCU 时钟**不同源**，`tick_ms` 无参考意义，只能估偏移，
  而偏移会随两时钟晶振漂移（典型 20~50 ppm，一天漂 2~4 秒）
- **诚实的结论**：这种精度对导航**没有实际价值**。真正有价值的是
  「`header.stamp` 用 `now()` 而非 `tick_ms` 换算」这一条——
  保证 `/odom` 的时间戳单调递增（TF 要求），这就够了。

> 不要在这里过度设计。协议文档提到 tick_ms 是为了「你知道有这个坑」，
> 不是要求你实现 PTP。

### 2.1 `src/navbot_bridge/navbot_bridge/protocol.py`（新建）

**职责**：帧的组装与解析。**不碰串口、不碰 rclpy**——这是它能单测的原因。

| 导出 | 签名要点 | 实现要点 |
|---|---|---|
| `FRAME_FIELD_COUNT` | 常量 `= 11` | 单一事实来源，别在代码里散落 `11` |
| `build_odom_frame(...)` | 11 个入参 → `str` | 格式串与 `fake_chassis.py:104` **逐字符一致** |
| `parse_odom_frame(line)` | → `dict \| None` | ★ 判据：`len(parts) == 11 and parts[0] == "O"`，异常返回 `None` |
| `build_velocity_frame(seq, vl, vr)` | → `str` | `V,<seq>,<vel_l>,<vel_r>\n` |
| `parse_velocity_cmd(line)` | → `dict \| None` | 字段数必须 == 4 |

**关键实现要点**：

1. **字段数严格等于 11，少一个多一个都返回 `None`**
   理由（协议 §五）：截断的帧不能猜，版本不匹配的帧不能忽略。
   这是 v1 协议「固定字段数」设计带来的红利。
2. **`int()` 会抛 `ValueError`**，必须 try/except 包住整个转换。
   `test_protocol.py:177` 专门测了 `O,abc,...` 这个 case。
3. **返回 `None` 而不是抛异常**。解析失败是常态（50Hz 里混入乱码），
   让调用方决定计数，不让异常控制流。
4. **用 `line.strip()` 先去空白**。串口可能带 `\r\n`。

**容易踩的坑**：

| 坑 | 后果 | 规避 |
|---|---|---|
| 字段数写成 `>= 11` | 协议升级后旧解析器默默接受新字段，静默错位 | 严格 `==` |
| 忘记 `parts[0] != "O"` | 收到 `V` 帧时误解析成 O 帧（字段数不同，尚能挡住；但若将来帧头复用会出事） | 双重判据 |
| `int()` 未捕获 | 一个坏帧崩掉整个节点 | try/except 全包 |
| 帧头判断用 `startswith("O")` | `OK,...` 开头会误判 | 先 `split(",")[0] == "O"` |

**自测方法**：

### 2.2 `src/navbot_bridge/navbot_bridge/kinematics.py`（新建）

**职责**：三个换算公式 + 编码器换算。全部纯函数、SI 与 mm/s 互转明确。

| 导出 | 公式 | 必须记住 |
|---|---|---|
| `cmdvel_to_wheel_mms(v, omega, wheel_sep)` | `v_l = v - ω·L/2`；`v_r = v + ω·L/2` | ★ 用 `round` **不要用 `int()`** |
| `wheel_mms_to_cmdvel(vl_mms, vr_mms, wheel_sep)` | `v = (v_l+v_r)/2`；`ω = (v_r-v_l)/L` | 算 `/odom` 的 `twist` |
| `enc_delta_to_mms(delta, R, ppr, dt)` | `Δenc · 2πR/ppr / dt · 1000` | 注意 `*1000` 转 mm/s |
| `apply_deadband(delta, threshold)` | `|Δ| ≤ threshold → 0` | ★ 见 D4 |

**关键实现要点**：

1. ★★ **`round` 而非 `int()`**：这是本项目最容易「看起来对其实错」的一处。
   `int()` 是向零截断，`int(-0.6) == 0`，对负数系统性偏慢。
   `test_protocol.py:225-227` 专门测了：`-0.0006 m/s` 必须得到 `-1 mm/s`，
   得 0 就说明用了 `int()`。
2. **死区阈值取 2 脉冲**。`test_protocol.py:276-278` 算过：2 脉冲 = 9.67 mm/s。
   阈值太大则真实慢速爬行被吞掉（如 5 mm/s 只能产生 1 脉冲/周期 → 会被误杀），
   所以不要取 5 以上。
3. **积分步长 `dt` 用实测值**，不要写死 0.02。
   串口抖动会让实际间隔在 18~25ms 波动，写死会引入系统性速度误差。

**容易踩的坑**：

| 坑 | 后果 | 规避 |
|---|---|---|
| 用 `int()` 截断 | 负速度系统性偏慢，低速几乎不动 | `round()` |
| 忘了 `*1000`（m/s→mm/s） | 慢 1000 倍，表现为「车几乎不动」 | 单测锚点：41 脉冲/20ms → 198 mm/s |
| 死区用 `>` 而非 `>=` | 边界差 1 脉冲 | 单元测试覆盖 `threshold` 本身 |
| 积分用写死 `dt=0.02` | 频率抖动时速度偏 | 用两帧时间戳之差 |

**自测方法**：直接跑现成的 `test_protocol.py`——它第 4/5/6/7 组就是这四个函数的自测。
**照抄公式，不要重写**。`test_protocol.py:28-35` 解释了原因：
> 「测试的价值在于独立实现一遍再对比，抄同一份代码反而测不出错」

所以正确做法是：把公式**照抄**进 `kinematics.py`（保证行为一致），
同时把 `test_protocol.py` 复制进 `test/`（保证后续改动不回归）。

### 2.3 `src/navbot_bridge/navbot_bridge/odometry.py`（新建）—— 位姿积分

**职责**：把编码器增量累积成 `x, y, yaw`。**只做数学，不碰 ROS、不碰串口。**

| 导出 | 要点 |
|---|---|
| `class OdomIntegrator` | 持有 `x, y, yaw` 与上次位姿 |
| `.update(v, omega, dt)` | 核心：积分一步 |
| `.reset()` | 收到重启特征帧时归零 |
| `.drift_warning(...)` | 可选：长期未更新时告警（对应 R7） |

**关键实现要点**：

1. **用中点法积分，不是前向欧拉**：

   | 方法 | 公式 | 误差特征 |
   |---|---|---|
   | 前向欧拉 | `x += v·cos(yaw)·dt` | 转弯时系统性偏内，误差随 `ω` 线性增长 |
   | **中点法（推荐）** | `θ_mid = yaw + ω·dt/2`；`x += v·cos(θ_mid)·dt` | 二阶精度，20ms 步长下误差可忽略 |

   原地转 360°（`v=0, ω=1`）时，前向欧拉**不产生位置漂移**（因为 `v=0`），
   但走弧线时会累积。`fake_chassis.py:84-87` 用了前向欧拉（注释说「20ms 步长下误差可忽略」），
   本项目跟用它可以保持一致，但你自己写时用中点法更好。

2. **`yaw` 归一化到 `(-π, π]`**。不清洗的话，`yaw` 会单调增长到几千弧度，
   转 `sin(yaw)`/`cos(yaw)` 虽然还对，但存进 `quaternion` 后数值精度会退化。

3. **四元数转换手写，别加依赖**。yaw→quat 只有 4 行：

   ```
   half = yaw / 2.0
   (x, y, z, w) = (0.0, 0.0, sin(half), cos(half))
   ```

   为此引入 `transforms3d` 不值得——而且 `nav2_params.yaml:125`
   已经要求 `robot_base_frame: base_footprint`，坐标系名字是硬约束。

**容易踩的坑**：

| 坑 | 后果 | 规避 |
|---|---|---|
| `dt` 用写死值 | 频率抖动引入速度误差 | 用实测差值 |
| yaw 不归一化 | 长时间运行后数值精度退化 | 每步 `% 2π` |
| 用 `int` 累加位置 | 位置永远走不动 | 全程 float |
| 累计脉冲差值用 `enc_l - prev` 但 `prev` 未初始化 | 第一帧得到巨大 `Δ` → `/odom` 瞬移 | 首次帧只记录不积分 |

**自测方法**（无硬件可做，务必做）：

```bash
/usr/bin/python3 -c "
import sys, math; sys.path.insert(0, 'src/navbot_bridge')
from navbot_bridge.odometry import OdomIntegrator
# 场景 A：v=0.2 走 1 秒 → x 应 ≈ 0.2
o = OdomIntegrator()
for _ in range(50): o.update(0.2, 0.0, 0.02)
print(f'走1秒 x={o.x:.4f} 期望≈0.2000'); assert abs(o.x-0.2) < 1e-6
# 场景 B：v=0, ω=1 原地转 2π → x,y 应≈0, yaw≈2π
o = OdomIntegrator()
for _ in range(314): o.update(0.0, 1.0, 0.02)
print(f'转一圈 x={o.x:.5f} y={o.y:.5f} yaw={o.yaw:.4f}')
assert abs(o.x) < 1e-3 and abs(o.y) < 1e-3
# 场景 C：走一个整圆，验证弧长闭合
o = OdomIntegrator(); R=0.5; w=0.4
for _ in range(int(2*math.pi/w/0.02)): o.update(R*w, w, 0.02)
print(f'整圆闭合 x={o.x:.4f} y={o.y:.4f}'); assert abs(o.x)<0.02
"
```

> 场景 C 最能暴露积分公式的错：走整圆必须回到原点，误差大说明用了前向欧拉。

### 3.1 `navbot_bridge/serial_io.py`（新建）—— 串口收发层

**职责**：只管「字节进、字节出、缓冲区拼接」。**不解析、不发布**。

| 导出 | 职责 | 关键点 |
|---|---|---|
| `class SerialLink` | 打开/关闭/重连 | 打开失败 → warn 节流，**不崩** |
| `.connect()` | 建立 `serial.Serial` | `timeout=0.005`（D3） |
| `.read_lines()` | → `list[str]` | ★ 核心难点：缓冲区残缺尾巴 |
| `.write_line(s)` | 写一帧 | 自动补 `\n` |
| `.is_open` | 属性 | |

**关键实现要点**：

1. ★★★ **跨 read 调用的半包处理**——本阶段唯一的真难点。

   串口 `read(256)` 返回的**不保证是完整一行**。可能返回：
   - 半行 `b"O,1234,-5820,5"`
   - 一行半 `b"O,1234,...\nO,1235,..."` ← **最常见**
   - 乱码 `b"~~~GARBAG"`

   正确做法：维护实例级 `self._buf`（`bytes`），
   每次 read 后 `self._buf += chunk`，然后 `while b"\n" in self._buf:` 切分。

   **错误做法**：`chunk.decode().split("\n")` 丢残缺尾巴 →
   **随机丢掉整帧**，表现为 `/odom` 频率从 50 掉到 35，TF 抖动，极难定位。

   参照实现：`fake_chassis.py:234-237`（它处理的是下行，收 V 帧，逻辑完全对称）。

2. **重连不崩，且日志节流**（协议 §五：5 秒最多一条）。
   拔线时 `read` 抛 `SerialException`，捕获后 `is_open=False`，
   下一周期再试连。**无限重试但不退出节点**。

3. **`write_line` 要防"写死了"**：`Serial.write` 可能只写了一部分（少见但存在）。
   稳妥写法是循环直到写完或超时。

**容易踩的坑**：

| 坑 | 后果 | 规避 |
|---|---|---|
| `timeout=None` | 永久阻塞，节点卡死 | `timeout=0.005` |
| 丢残缺尾巴 | 随机丢帧，TF 抖动 | 实例级 buffer |
| 异常不捕获 | 拔线即崩 | try/except 全包 |
| warn 每次都打 | 刷屏，日志几十万行 | 节流（记上次 warn 时间） |
| `errors='ignore'` 吞掉解码错误 | 坏帧变成空串，掩盖问题 | `errors='replace'` 并计数 |

**自测方法**（不需要真串口）：

```bash
/usr/bin/python3 -c "

from navbot_bridge.serial_io import FrameBuffer
fb = FrameBuffer()
# 模拟跨包：一帧半 + 半帧

assert fb.pop() is None, '半帧不该返回！'

print('✓ 半包/粘包处理正确')
"
```

> 建议把 `FrameBuffer` 做成**独立于 `serial` 的纯类**，
> 这样它可被单测覆盖，不依赖 pyserial 和真串口。这是本项目的关键可测性设计。

### 3.2 `navbot_bridge/odom_publisher.py`（新建）—— 上行数据处理

**职责**：把解出的字段变成「要不要发布 /odom」这个决定，以及位姿更新。

| 导出 | 职责 |
|---|---|
| `class OdomProcessor` | 持有 `OdomIntegrator` + 上次位姿 + 坏帧计数 |
| `.process(frame_dict, now)` | → `OdomState \| None` |
| `.stats` | 坏帧数、丢帧数、频率 |

**关键实现要点**：

1. ★★★ **三层异常处理**（协议 §五，这是本项目的核心设计）：

   | 层 | 触发 | 动作 |
   |---|---|---|
   | 连接层 | 串口打不开 / 拔线 | 重连 + warn 节流（5s 一条） |
   | 数据层 | 字段数 ≠ 11、解析失败 | **静默计数，绝不刷屏** |
   | **时效层** | `seq` 连续 N 帧不增长 | **★ 停止发布 `/odom`** + 只警告一次 |

2. ★ **seq 停滞检测**：`--no-seq` 注入时 `seq` 恒为 0。
   判据：`now - last_seq_change_time > 0.5s` 且 `seq` 与上次相同 → 数据陈旧。
   用**标志位**保证只警告一次，否则会每秒刷一条。

3. **丢帧统计**：`(最大seq - 最小seq + 1) - 收到帧数`。
   这就是 `seq` 存在的意义（协议 §二【2】）。把它打进日志，能说清「坏数据块每 5 秒来一次」这类问题。

4. **坏帧计数要有上限或定期汇总**。`verify_e2e.sh:503` 断言
   「日志行数 < 500」，所以坏帧**绝不能逐帧 warn**——每 100 帧汇总一次即可。

**容易踩的坑**：

| 坑 | 后果 | 规避 |
|---|---|---|
| 坏帧逐帧 warn | 日志刷屏，`verify_e2e.sh` 判失败 | 只计数，定期汇总 |
| 数据陈旧时继续发旧值 | 代价地图滚动、定位漂移（现象隐蔽） | ★ 停止发布 |
| `seq` 停滞每帧都警告 | 刷屏 | 标志位 |

### 3.3 `navbot_bridge/cmd_vel_relay.py`（新建）—— 下行数据处理

**职责**：`/cmd_vel` → 轮速 mm/s → V 帧。**同时承担安全兜底。**

| 导出 | 职责 |
|---|---|
| `class CmdVelRelay` | 订阅缓存 + 20Hz 节流下发 + 超时停车 |
| `.on_cmd_vel(msg)` | 只缓存，**不直接发** |
| `.tick(now)` | 20Hz 定时器调用；超时则发零速 |

**关键实现要点**：

1. ★ **不能「收到就发」**。`/cmd_vel` 在 Nav2 里可能 100Hz  bursts，
   直接转发会打爆串口。必须**缓存最新值 + 20Hz 定时下发**
   （协议 §二：下行 20Hz）。

2. ★★★ **PC 侧也必须做失联停车**，不能只依赖 MCU。
   判据：距上次收到 `/cmd_vel` 超过 **100ms**（`nav2_params.yaml:505-506` 的
   `odom_topic: "odom"` / `odom_duration: 0.1` 给了 0.1s 这个量级参考），
   则下发 `V,seq,0,0`。
   MCU 侧有 500ms 保护（协议 §四），但 **PC 侧 100ms + MCU 侧 500ms 是两级**，
   比单靠 MCU 快 5 倍。

3. **限幅**。`nav2_params.yaml:217` 定 `max_vel_x: 0.22`。
   下发前 clamp 到安全范围，防止 Nav2 抖动给出离谱值直接把电机打飞。

4. **`v_l`/`v_r` 符号不要搞反**。
   协议 §三验算：`v=0, ω=0.5` → `v_l = -0.04`（左轮后退），`v_r = +0.04`（右轮前进）→ 原地左转。
   搞反了车会朝错误方向转，是「负号只在原地转时暴露」的隐蔽 bug。

**容易踩的坑**：

| 坑 | 后果 | 规避 |
|---|---|---|
| 收到就转发 | 串口打爆，MCU 解析错乱 | 20Hz 定时 |
| 没有超时停车 | Nav2 停了但车还在走 | 100ms 超时归零 |
| 无限幅 | 电机被打飞 | clamp 到 `max_vel_x` |
| 左右轮符号反 | 原地转方向反，直行正常 | 用 `v=0,ω=0.5` 单测 |
| `V` 帧 `seq` 恒 0 | MCU 侧丢指令检测失效 | 递增 |

**自测方法**：

```bash
/usr/bin/python3 -c "
import sys; sys.path.insert(0,'src/navbot_bridge')
from navbot_bridge.cmd_vel_relay import CmdVelRelay
r = CmdVelRelay(timeout=0.1, max_v=0.22, wheel_sep=0.16)
r.on_cmd_vel(v=0.0, omega=0.5, now=0.0)      # 原地左转
print(r.build_frame(seq=1))
assert r.build_frame(seq=1).strip() == 'V,1,-40,40', '★ 左转符号反了！'
r.on_cmd_vel(v=0.0, omega=0.0, now=5.0)      # 5s 无新指令
assert r.wheel_l == 0 and r.wheel_r == 0, '★ 超时未停车！'
print('✓ 逆解与超时停车正确')
"
```

**必须声明的 ROS 参数**（★ 名字必须和 `verify_e2e.sh:396-399` 完全一致）：

| 参数 | 类型 | 默认 | 验证来源 |
|---|---|---|---|

| `wheel_radius` | `float` | `0.0325` | `:398` |

| `base_frame` | `str` | `base_footprint` | 阶段 6 TF 断言 |
| `odom_frame` | `str` | `odom` | `verify_e2e.sh:434` |
| `publish_rate` | `float` | `50.0` | `:419` 期望 40~60 |
| `deadband_pulses` | `int` | `2` | D4 |
| `stale_timeout` | `float` | `0.5` | R7 |

**关键实现要点**：

1. ★★★ **`/odom` 的 frame_id 写错，Nav2 一定起不来**。
   `verify_e2e.sh:433-443` 专门断言这两个值：
   - `header.frame_id` == `odom`
   - `child_frame_id` == `base_footprint`

   而 `nav2_params.yaml:31,43,125` 反复强调：AMCL 的 `base_frame_id`、
   代价地图的 `robot_base_frame`、Gazebo `diff_drive` 的 `robot_base_frame`
   **三处都必须叫 `base_footprint`**，不是 `base_link`。
   `nav2_params.yaml:38-41` 解释了原因：三处不一致 ⇒ `odom→base` 和 `map→odom` 对不上 ⇒ 定位持续漂移。

2. ★ **TF 的 `child_frame_id` 和 `/odom` 的 `child_frame_id` 必须一致**，
   且 TF 要用 `qos` 低一点（`TransformBroadcaster` 默认 10），
   否则高频 TF 会被 QoS 丢弃。

3. **`/joint_states` 角速度单位是 rad/s**，需从 mm/s 换算：

   ```
   ω_wheel = v_wheel_mm_s / 1000 / wheel_radius
   ```

   ★ 别忘了 `left_wheel_joint` 和 `right_wheel_joint` 的**旋转方向**：
   前进时两轮都是负角速度还是正角速度，取决于 URDF 的 joint 轴方向。
   搞反了 RViz 里轮子倒转。**这是阶段 6 的验证项**。

4. **`use_sim_time` 参数**。真机为 `false`。
   桥节点自己用 `self.get_clock().now()`，不要直接 `time.time()`——
   否则仿真时（`use_sim_time:=true`）时间戳会错乱。

5. **`main()` 里必须有 `try/finally` 关串口**，
   否则 Ctrl+C 时串口句柄泄漏，`fake_chassis` 重连时报 busy。

**容易踩的坑**：

| 坑 | 后果 | 规避 |
|---|---|---|
| `base_link` vs `base_footprint` | 定位持续漂移，且现象隐蔽 | 全部用 `base_footprint` |
| 用 `time.time()` | 仿真下时间戳错乱 | `get_clock().now()` |
| 轮子角速度方向反 | RViz 里倒转 | 阶段 6 验证 |
| 只发 position 不发 velocity | RViz 轮子卡在原位 | 三个字段都填 |
| TF qos 太高被丢 | TF 断续 | 用默认 10 |

**自测方法**：

### 6.3 故障注入矩阵（★ 逐个手动验一遍）

`fake_chassis.py:20-24` 提供了 4 个开关。每个都要单独跑：

| 开关 | 注入什么 | 期望的桥的行为 | 验什么 |
|---|---|---|---|
| `--stall-after 100` | 发 100 帧后静默 | 桥存活；`/odom` 停止更新；**只警告一次** | R7 时效层 |
| `--garbage-every 5` | 每 5 帧插乱码 | 桥存活；`/odom` 频率仍 40~60；日志不涨 | R6 数据层 |
| `--no-seq` | `seq` 恒 0 | 桥**停止发布** `/odom` | R7 ★核心 |
| `--zero-drift 2` | 静止时 +2 脉冲/周期 | `/odom` **不爬行**（死区生效） | D4 死区 |

**推荐一次跑全流程的命令序列**：

```bash
# 逐个启动假底盘，观察桥的行为，每次跑完 kill
for mode in "--stall-after 100" "--garbage-every 5" "--no-seq" "--zero-drift 2"; do
  echo "=== 注入 $mode ==="
  python3 fake_chassis.py --port /tmp/ttyV0 --rate 50 $mode &
  sleep 6
  echo -n "  桥存活: "; kill -0 $BRIDGE_PID 2>/dev/null && echo YES || echo NO
  echo -n "  /odom 频率: "; timeout 5 ros2 topic hz /odom 2>/dev/null | grep -oP 'average rate: \K[0-9.]+' | head -1
  echo -n "  bridge.log 行数: "; wc -l < _e2e_logs/bridge.log
  kill %2 2>/dev/null; sleep 1
done
```

**★ `--no-seq` 是最重要的一项**。
多数实现会在这里失败——他们会「继续发旧数据」，因为这样 `/odom` 看起来一直在动，
`ros2 topic hz` 甚至还能测出频率。但本项目要求停止发布（协议 §五）。
**判据：`--no-seq` 注入后 `ros2 topic hz /odom` 应无输出或频率骤降。**

### 6.4 物理自测（★ 无硬件也能做，验单位链条）

`fake_chassis.py:40-42` 指出这是「无硬件条件下唯一能验里程计正确性的办法」。

**做法**：让假底盘持续发 `V,0,200,200`（直行 200 mm/s），观察 `fake_chassis.py` 每秒打印的状态行：

```
[状态] 已发 250 帧 | 位姿 x=+3.000m y=+0.000m yaw=+0.000rad | 目标轮速 L= 200 R= 200 mm/s
```

**判据**（用测试锚点反推）：

| 检查 | 计算 | 期望 |
|---|---|---|
| 直行 5 秒 | `v = 0.2 m/s` × 5s | `x ≈ 1.0 m` |
| 原地转 2π | 单轮走 `2π × 0.08 = 0.5027 m` | `yaw ≈ 6.283 rad`，`x,y ≈ 0` |
| 单位没乘 1000 | 若 `x` 差 1000 倍 | 说明漏了 `*1000` |
| 轮距算错 | 转一圈后 `x,y ≠ 0` | 说明 `wheel_separation` 不对 |
