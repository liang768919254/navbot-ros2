# ============================================================================
# navbot_protocol.md —— PC ↔ STM32 底盘 通信协议 v1
# ============================================================================
# 这是 P3 项目「真机路线」的接口契约。
#
# ★★ 为什么协议要单独写成一份文档、放在代码之外？
#    因为它是「两端共同的约定」—— PC 侧 Python 和 MCU 侧 C 各自实现一遍，
#    任何一端改字段，另一端必须同步改。协议写在文档里，改之前能看见影响面；
#    只写在代码里，就成了两个各说各话的孤岛，调试时你会怀疑人生。
#
# ★ 这份协议直接继承了 sensor_bridge 阶段三的经验：
#    v1 协议的问题（字段数"猜"格式、无时间戳、无丢帧检测）在这里一次修掉。
#
# ============================================================================
# 一、总体结构
# ============================================================================
#
#   【上行】STM32 → PC（底盘状态报）
#     用途：提供 /odom 的原始数据 + 轮速反馈
#     频率：50 Hz（20 ms 一帧）
#     格式：ASCII 逗号分隔 + '\n' 结尾（人类可读，调试期价值极高）
#
#   【下行】PC → STM32（速度指令）
#     用途：把 /cmd_vel 转成左右轮的目标速度
#     频率：20 Hz（超过 50 ms 没收到新指令 → 自动停车，安全兜底）
#     格式：ASCII 逗号分隔 + '\n' 结尾
#
# ★★ 为什么上下行都用 ASCII 而不是二进制？
#    这是「学习期 vs 量产期」的取舍：
#      ASCII：能用串口助手直接看、直接敲，调试成本接近零；
#             代价是带宽利用率低（本场景 50Hz × 40 字节 = 2KB/s，
#             波特率 115200 = 11.5KB/s，占用不到 20%，完全够）
#      二进制：省带宽、有 CRC，但调试时看不到人话，学习期不合适
#    → 本项目选 ASCII。等做了 CAN 或多电机系统再上二进制（那是阶段三的事）。
#
# ============================================================================
# 二、上行协议（STM32 → PC）
# ============================================================================
#
#   帧格式（11 个字段，★ 字段数是固定的 —— 这是 v1 的改进）：
#
#     O,<seq>,<enc_l>,<enc_r>,<vel_l>,<vel_r>,<pwm_l>,<pwm_r>,<vbat_mv>,<tick_ms>,<temp_c100>\n
#
#   逐字段说明：
#
#   | 字段     | 类型  | 单位    | 说明                                      |
#   |----------|-------|---------|-------------------------------------------|
#   | 帧头     | char  | -       | 固定 'O'（Odom），用来在一堆乱码里找同步头 |
#   | seq      | u32   | 计数    | 帧序号，从 0 递增。★ 丢帧检测靠它          |
#   | enc_l    | i32   | 脉冲    | 左编码器累计计数（可正可负）               |
#   | enc_r    | i32   | 脉冲    | 右编码器累计计数                           |
#   | vel_l    | i32   | mm/s    | 左轮线速度，毫米每秒（整数，避免浮点）     |
#   | vel_r    | i32   | mm/s    | 右轮线速度                                 |
#   | pwm_l    | i16   | -1000~1000 | 左电机当前 PWM 占空比                   |
#   | pwm_r    | i16   | -1000~1000 | 右电机当前 PWM 占空比                   |
#   | vbat_mv  | u16   | mV      | 电池电压（★ 这个字段救过很多人的车）      |
#   | tick_ms  | u32   | ms      | MCU 侧毫秒时间戳（★ 用于时间对齐）        |
#   | temp_c100| i16   | 0.01°C  | 驱动板温度（可选，没有就填 0）             |
#
#   示例帧：
#     O,1234,-5820,5815,120,118,420,415,11850,184320,2510
#
# ----------------------------------------------------------------------------
# ★★ 三个关键设计决定，每个都有明确理由
# ----------------------------------------------------------------------------
#
# 【1】为什么速度用 mm/s 整数，不用 float？
#     因为 MCU 上没有 FPU（或开了 FPU 但 printf %f 极慢），
#     浮点格式化会吃掉大量 CPU，在 50Hz 的实时循环里是致命的。
#     ★ 这一条是从 sensor_bridge 阶段三「v3 全整数定点」直接继承来的经验。
#     精度换算：1 mm/s 的量化误差对 0.2 m/s 的车来说是 0.5%，完全可接受。
#
# 【2】为什么必须有 seq？
#     没有 seq，你无法区分这两种情况：
#       (a) 车没动，所以编码器没变     ← 正常
#       (b) 串口丢了 3 帧，数据不连续  ← 故障
#     ★ 这是 sensor_bridge 阶段二那次「topic hz = 0.198」事故的直接教训：
#       当时就是因为不知道「坏数据块每 5 秒来一次」，查了很久。
#     有了 seq，PC 侧统计 (收到的最大 seq - 收到的帧数) 就是丢帧数，
#     一行日志就能说清楚。
#
# 【3】为什么必须有 tick_ms？
#     因为 PC 侧的 header.stamp 标的是「数据到达 PC 的时刻」，
#     不是「数据在 MCU 上采样的时刻」。两者相差：
#       串口传输 + USB 转换 + 内核缓冲 ≈ 1~2 ms（115200bps 下）
#     慢速场景无所谓，但做里程计积分时，这 2ms 会造成系统性误差。
#     ★ 有了 tick_ms，可以做「到达时刻 - 传输延迟估计 = 采样时刻」的校正。
#     这也呼应了 sensor_bridge 复盘里那句：
#     「header.stamp 标的是到达时刻不是采样时刻，要校正得靠 mcu_tick_ms」。
#
# ============================================================================
# 三、下行协议（PC → STM32）
# ============================================================================
#
#   帧格式（4 个字段）：
#
#     V,<seq>,<vel_l>,<vel_r>\n
#
#   | 字段   | 类型 | 单位   | 说明                                       |
#   |--------|------|--------|--------------------------------------------|
#   | 帧头   | char | -      | 固定 'V'（Velocity）                        |
#   | seq    | u32  | 计数   | 指令序号（可用于 MCU 侧丢指令检测）         |
#   | vel_l  | i32  | mm/s   | 左轮目标线速度                              |
#   | vel_r  | i32  | mm/s   | 右轮目标线速度                              |
#
#   示例帧：
#     V,567,120,-120          ← 原地左转（左轮前进，右轮后退）
#
# ----------------------------------------------------------------------------
# ★★ 差速运动学：PC 侧把 /cmd_vel 的 (v, ω) 转成左右轮速度
# ----------------------------------------------------------------------------
#
#   公式（记住它，面试会问）：
#
#     v_l = v - ω × L / 2
#     v_r = v + ω × L / 2
#
#   其中 L = 轮距 = 0.16 m（★ 必须和 URDF 里 wheel_sep 完全一致）
#
#   Python 实现：
#
#     L = 0.16
#     v_l = v - omega * L / 2.0
#     v_r = v + omega * L / 2.0
#     # 转成 mm/s 整数（四舍五入，不是截断 —— 截断会带来系统性偏慢）
#     vel_l_mms = int(round(v_l * 1000))
#     vel_r_mms = int(round(v_r * 1000))
#
#   验算（v=0.2 m/s, ω=0）：
#     v_l = 0.2, v_r = 0.2  → 直行，两轮同速 ✓
#   验算（v=0, ω=0.5 rad/s）：
#     v_l = -0.04, v_r = +0.04  → 原地旋转，两轮反向 ✓
#
# ============================================================================
# 四、★ 安全兜底：失联自动停车（必做，不做会撞墙）
# ============================================================================
#
#   MCU 侧必须实现「指令超时保护」：
#
#     每收到一条 V 指令，就刷新 last_cmd_tick。
#     在主循环里检查：
#       if (now_tick - last_cmd_tick > 500)   // 500ms 没新指令
#           set_motor_speed(0, 0);            // 立即停车
#
#   ★★ 为什么是 500ms 而不是更大？
#      PC 侧发指令是 20Hz（50ms 一条），500ms = 丢掉 10 条指令，
#      已经能确定「不是偶发丢包，是对端真的挂了」。
#      再大就危险（0.2m/s × 1s = 20cm，够撞到东西了）；
#      再小会误触发（串口偶然卡一下 3 条指令就停了，很难开）。
#
#   ★ 这条保护的实战价值：
#      WiFi 断了 / 你的 Python 节点崩了 / 你手滑 Ctrl+C 了 ——
#      车都会自己停下来。没有它，你会亲眼看着车撞墙然后追悔莫及。
#     这是「真机项目」和「仿真项目」最重要的区别之一。
#
# ============================================================================
# 五、★ PC 侧收到坏数据怎么办（三层异常处理，继承 sensor_bridge 经验）
# ============================================================================
#
#   连接层异常（串口打不开 / 拔线）：
#     → 重连，不崩节点。warn 日志节流（5 秒最多一条）
#
#   数据层异常（乱码 / 半包 / 字段数不对 / 校验失败）：
#     → 静默计数，绝不刷屏
#     ★ 判据：字段数 != 11 就当坏帧丢掉。这是「固定字段数」带来的红利 ——
#       v1 协议那种「靠字段数猜格式」的做法在这里彻底消失了。
#
#   时效层异常（seq 长时间不增长 = 数据陈旧）：
#     → 暂停发布 /odom（★ 关键！不能发旧数据当新数据）
#       + 只警告一次（用标志位，别每秒刷一条）
#     ★★ 为什么必须「暂停发布」而不是「继续发旧值」？
#       因为 Nav2 的代价地图和 AMCL 会把旧位姿当真值用，
#       结果就是「车明明停了，代价地图还在滚动」，
#       进而导致定位漂移、规划错乱 —— 而且现象很隐蔽。
#
# ============================================================================
# 六、波特率与线路
# ============================================================================
#
#   波特率：115200（8N1，无流控）
#     ★ 为什么不用 9600：50Hz × 40 字节 ≈ 2KB/s，9600bps 只有 960B/s，不够
#     ★ 为什么不用 921600：115200 已经富余 5 倍，再高对 USB 转串芯片要求高
#
#   预期实测数据（供你对照）：
#     ros2 topic hz /odom        → 约 50 Hz
#     ros2 topic hz /scan        → 约 10 Hz（雷达自己的频率）
#     上行带宽占用               → 约 18%
#
#   ★ 若 hz 明显低于 50：先查 MCU 侧有没有漏 setvbuf（见 firmware 文件里的注释）
#
